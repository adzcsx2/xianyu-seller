# 开发规范

[返回 README](./README.md) · [上一篇：架构设计](./01-架构设计.md) · [下一篇：修复路线图](./03-修复路线图.md)

## 1. 适用范围与事实优先级

适用于全局知识库数据层、迁移、领域服务、FastAPI、AI 运行时、React 页面、测试和 API 目录。事实冲突按“本轮用户要求 → 运行源码/只读数据 → 当前 seed → 本计划 → 旧计划/prompt”处理。无法验证的事实标 `unknown`，不得猜测绑定或商品业务。

## 2. 命名与职责

统一术语：

- `knowledge base`：全局知识库实体；
- `binding`：商品与知识库的关联；
- `fact`：买家可见事实；
- `source`：管理侧来源引用；
- `rule`：内部业务规则；
- `qa entry`：公开问答条目；
- `reply style`：全局语气，不是业务规则；
- `engine guard`：不可由知识库关闭的订单/秘密安全边界。

禁止继续用 `ProductKnowledgeDocument` 表示全局知识库，也禁止 UI 用“知识项目”指代绑定。新类型使用 `KnowledgeBase*`、`KnowledgeBinding*`、`AIReplyStyle*`。

## 3. ID、key、文本和数量边界

| 字段 | 规则 |
| --- | --- |
| `id` | 服务端 UUID 字符串；客户端创建时不得指定 |
| `base_key` | 1～80 字符，`^[a-z0-9][a-z0-9._-]*$`，全局唯一 |
| `name` | trim 后 1～80 字符，全局唯一，纯文本 |
| `description` | 0～500 字符，纯文本 |
| 各内容 key | 1～80 字符，同一库+类型内唯一，格式同 base key |
| title/name | 1～120 字符，纯文本 |
| fact content / qa answer | 1～800 字符，买家可见纯文本 |
| source reference/notes | 各 0～500 字符；管理侧，不入模型 |
| questions | 0～20 项，每项 1～80 字符 |
| keywords | 1～30 项，每项 1～32 字符 |
| source_ids | 0～8 个同库 UUID，去重保序 |
| priority | 严格整数 -100～100，布尔值不得当整数 |
| reply_style | trim 后 1～1000 字符，纯文本 |
| 每库 facts/sources/rules/qa | 各最多 200，四类合计最多 500 |
| 管理请求 | 规范化 JSON 不超过 512 KiB |

所有数组去重后保留首次顺序。JSON 使用 `ensure_ascii=False` 和稳定 separators；未知字段由 Pydantic `extra='forbid'` 拒绝。

## 4. 数据库规范

- 新全局内容表不得出现 `user_id/cookie_id/owner_id/account_id`；只有 bindings 表出现 cookie/item。
- 所有方法沿用 `DBManager` 的锁与连接，不新增 repository 连接或数据库文件。
- DDL 使用 `CREATE TABLE/INDEX IF NOT EXISTS`，但数据迁移必须依赖 marker，而不是“库不存在就重建”。
- 写聚合事务顺序：读取 base version → 比对 expected → 验证引用/唯一性 → mutation → base version+1/checksum → commit。
- 捕获异常后 rollback 并抛出可识别领域异常，禁止返回模糊 False。
- binding add 使用数据库唯一约束；先查仅用于友好错误，不代替约束。
- base 全局删除在一个事务中先记录 binding count，再删 bindings、四类内容、base；异常全部回滚。
- source 删除先统计同库 fact/rule/qa 的 source_ids 引用；存在引用返回 `KnowledgeSourceInUse`，不得隐式修改其他内容。
- 删除 item 时显式删除 bindings 兜底；删除 cookie 的既有级联也要由测试证明不会留孤儿。
- 新表不得加入通用 `/admin/data/{table_name}` 白名单。
- 旧 `ai_product_knowledge_*` 与 `ai_reply_settings` 旧列本计划不 DROP，不做破坏性 schema rewrite。

领域异常固定为：

```text
KnowledgeNotFound                  → 404
KnowledgeVersionConflict           → 409
KnowledgeKeyConflict               → 409
KnowledgeBindingConflict           → 409
KnowledgeSourceInUse               → 409
KnowledgeValidationError           → 422
KnowledgeMigrationPrecondition     → 启动失败/明确 ERROR，不写 marker
```

500 响应不得拼接 SQL、绝对路径、数据库异常全文或内容正文。

## 5. 迁移规范

迁移键固定为 `global-knowledge-v2-passistant-20260907`。迁移必须满足：

1. marker 已存在：立即 no-op，不比较“Passistant 是否还存在”；
2. marker 不存在：只读验证 seed v2、目标 item 和旧数据证据；
3. 目标 `1081710901648` 不存在或已确认产品身份不匹配：抛出前置条件错误，零写入；
4. 创建一个 `base_key=passistant` 的全局库及四类内容；
5. 仅创建 `(target_cookie,1081710901648,passistant_id)` binding；
6. 显式断言 `741903197018` 和所有其他 item 无新 binding；
7. 写全局 reply style 默认值；不复制旧 prompt；
8. 最后在同一事务写 marker 并 commit。

不得按旧文档数量循环创建全局库；不得把所有拥有相同 checksum 的商品都绑定；不得通过标题模糊匹配选择第一件商品。正确 cookie 必须从包含目标 item 的现有 `item_info` 唯一确定。

迁移输入若已经存在用户创建的 `passistant` key 且 marker 不存在，停止并要求人工处理，不能覆盖。

## 6. Passistant v2 内容规范

当前 `app/knowledge/passistant_public_v1.json` 的 20 个公开条目及其用户修改是受保护输入。实施前重新读取，不能用计划生成时的快照覆盖后续变化。

新增 `app/knowledge/passistant_v2.json`，固定 schema 为：

```text
schema_version: 2
base: {base_key, name, description}
sources: []
facts: []
rules: []
qa_entries: []
```

来源从旧 `source_refs` 去重成 source 实体；qa/fact 只保存 source ids/key。若 seed 使用稳定 source key 而数据库使用 UUID，导入器负责同事务映射。

内部规则必须覆盖：

- 安全/封号匹配及精确回复 `目前没有收到玩家反馈有封号情况出现。`；
- 源码、偏移、后台凭据、成本、供应渠道、其他买家等固定拒答 `这个问题涉及内部信息，暂不提供。`；
- 未问安全时不主动出现封号/安全/检测风险；
- 原价 ¥29.9/月、当前活动口径 3 折、活动价 ¥9.9/月、无已知结束时间；
- 当前活动价不接受额外砍价；
- 自动交付只能说明一般方式，不能宣称某笔订单已完成；
- 国际服/台服支持、国服不支持；安装、激活和 30 天权益。

引擎级规则不得放进可删除库作为唯一来源：支付/发货/退款/收货事实、系统事件绕过、secret/path/system prompt 泄露、超时失败关闭。

## 7. Rule schema 规范

每类 `config_json` 必须有独立模型：

```text
fixed_reply/topic_refusal:
  match_mode: any|all
  terms: 1..100 normalized strings
  response: 1..300 plain text

pricing_policy:
  currency: CNY
  original_price: decimal string
  current_price: decimal string
  promotion_label: string|null
  promotion_end: string|null

bargain_policy:
  max_discount_percent: 0..100
  max_discount_amount: >=0 decimal string
  max_rounds: 0..100
  floor_mode: current_price|fixed
  floor_price: decimal string|null

output_guard:
  forbidden_unless_asked: string[]
  fallback_mode: top_match|human_confirmation

model_instruction:
  instruction: 1..800 plain text
```

金额使用 Decimal/字符串，不用 float。未知 rule type、负金额、空 terms、冲突字段和超过预算均 422。首版 matcher 只支持规范化字面短语，不支持客户端正则，避免正则复杂度和超时面。

## 8. 运行时规范

- `load_snapshot(cookie_id,item_id)` 是唯一商品知识读取入口；其他模块不得直接扫描全局表。
- snapshot 读取 bindings 与所有 base version 应在一致读事务中完成，避免一半新一半旧。
- 无 binding 返回空 lists，不返回默认 Passistant 元数据。
- disabled base/rule/content 不参与运行；管理 API 仍回显以便恢复。
- 检索沿用 NFKC、casefold、空白折叠和稳定评分；每条结果携带 base/content key 供日志，但模型只得到 category/content/answer。
- 模型上下文固定最多 2500 字符、最多 5 条，先按全局排序再取，避免绑定越多无限增长。
- `source_ids/reference/notes`、matcher、rule config、priority、DB id、version、checksum 不进入模型。
- 固定规则在创建模型客户端前执行并断言零调用。
- 全局 reply style 作为单独 system section，放在事实之前；结构化 hard rule 在 style 之后重新声明，防止 style 覆盖。
- arbitrary `model_instruction` 只能追加当前商品业务，不得含“忽略/覆盖系统规则”、source 路径、secret 或代码执行指令；校验和输出 guard 双重保护。

## 9. 多库冲突规范

稳定规则：

```text
rule: (-priority, binding_sort_order, base_key, rule_key)
content: (-score, -priority, binding_sort_order, base_key, content_key)
```

- 相同固定 intent 只执行排序第一条；不同 response 同优先级记录 warning。
- pricing/bargain 不按排序覆盖，而是组合最严格边界；无法组合就不议价并人工确认。
- 同一标准化公开答案只注入一次。
- 任一库损坏不能让其他库 sources 泄露；损坏结构化 hard rule 应 fail closed，记录 key 并中止商品 AI 回复或转人工，不静默跳过后继续自由生成。

## 10. 全局回复风格规范

默认值精确为：

```text
语气自然、友好，略带俏皮，像真实的闲鱼卖家。优先用一到两句短句直接回答，可少量使用语气词；不要复述规则，不主动扩展买家没有询问的内容，避免客服腔、夸张承诺和连续表情。
```

style 可包含语气、长度、称呼、表情频率、是否简洁等表达维度。不得出现：

- 商品或知识库名称；
- 金额、折扣、议价轮次；
- 区服、安装、激活、交付、售后流程；
- 安全/封号固定话术或商业敏感规则；
- JSON rule、system prompt 标签、secret/path。

style 校验命中明显业务词时返回 422 并提示“商品业务请在知识库内部规则中配置”。不要把业务词表完整回显给客户端。

## 11. API 规范

- 新知识库全局 CRUD 只做认证，不调用 cookie owner 校验，也不接收 user_id。
- 商品 binding/preview 必须先验证当前用户 cookie scope，再验证 item 存在；非所属 cookie 统一 403，不泄露 item。
- response 使用明确 Pydantic 白名单；禁止直接返回 DB row dict，尤其是 sources notes、rule config 和运行 snapshot。
- 管理 detail 可以返回 sources/rules，但 preview/runtime response 必须使用不同模型。
- mutation 全部返回最新 version；409 至少返回 `current_version`，不回显内容正文。
- DELETE base 的确认不是服务端二阶段事务；前端先从 summary 获得 binding_count，再发送 DELETE，服务端以当前事务实际计数为准并在响应返回。若计数变化，删除仍按用户确认执行，但日志记录差异。
- 四个旧 `/items/{cookie_id}/{item_id}/ai-knowledge...` 路由固定返回 410，detail 只指向新资源路径；禁止兼容写、旧表读或双写。
- `app/reply_server.py::API_ROOTS` 必须加入 `knowledge-bases` 和 `ai-reply-style`，避免未知新 API 路径落入 SPA catch-all。
- API 索引和 Markdown 目录由生成器更新，不手改来掩盖源码不一致。

## 12. 前端规范

- `KnowledgeBase.tsx` 负责页面数据编排；四类复杂编辑器放在独立 modal 组件，目标每个新文件低于 500 行。
- 当前区域和全部区域使用不同 handler 命名：`handleUnbindKnowledgeBase` 与 `handleDeleteKnowledgeBase`，禁止都叫 delete。
- 行尾全局删除按钮必须 `event.stopPropagation()`，并有 `aria-label="删除知识库 <name>"`。
- 添加绑定弹窗已绑定项应禁用且显示“已添加”；即使前端过滤，仍处理服务端 409。
- 删除绑定弹窗只列 bound bases；确认文案包含“不会删除全部知识库中的内容”。
- 全局删除确认包含不可逆影响：facts/sources/rules/qa 和 N 个商品绑定；提交中按钮 disabled。
- 所有 dialog 支持 Escape/取消、明确标题、焦点可达；不使用浏览器原生 `window.confirm` 混杂现有反馈系统。
- 关闭有 dirty 内容的编辑器必须确认；409 不自动 rebase/覆盖。
- 四类内容空态、loading、error、disabled 和保存成功回读都要独立可见。
- 页面和 modal 按纯文本渲染，禁止 `dangerouslySetInnerHTML`。
- `AIReply.tsx` 的 global style 不随账号选择重置；`AccountList.tsx` 不再出现 custom prompt/议价业务编辑器。

## 13. 测试规范

- 使用 `unittest`/`unittest.mock`，patch 被测模块实际查找符号的位置。
- 数据库测试仅用 `TemporaryDirectory` 中 SQLite；运行 DB 只读审计和最终受控迁移分开。
- migration 测试必须含：一次成功、二次 no-op、中途 rollback、marker 存在但 base 被删不重建、错误商品不绑定、key 冲突阻断。
- 固定规则测试 mock `_create_openai_client`、`_generate_with_retry` 和知识检索，断言零调用。
- 未绑定商品测试不得仅断言“无 matches”，还要断言 Passistant fixed rule、price guard、output terms 和 prompt 都未加载。
- API 测试覆盖认证、商品 scope、无 owner 字段、409/404/422、response 脱敏和 side effect。
- 前端没有现成测试 runner 时，用 Python 静态合同 + Vite build；不得为了本任务引入新 JS 测试依赖。
- 测试不能通过修改生产默认值来迎合 fixture；生产代码不得包含 mock/stub。

## 14. 日志与可观察性

- migration：只记录 migration key、base/content/binding 计数、checksum 和状态。
- CRUD：记录 resource type/id 摘要、base version 和错误代码，不记录内容正文。
- runtime：记录 item 安全摘要、base keys、rule keys、match count、reply length；不记录 source、prompt、买家原文或完整 answer。
- 多库冲突记录 key/priority/选择结果，不记录固定回复正文。
- 任何日志都不得包含 API key、Cookie、token、密码、完整激活码、客户资料或本地绝对 source 路径。

## 16. 禁止操作

- 不 reset/checkout/覆盖用户未提交改动，不全仓格式化。
- 不直接写运行 SQLite，不手工删旧表，不用迁移启动逻辑反复重建内置库。
- 不新增用户/owner/admin/role 字段或权限页面。
- 不把 sources、matcher、内部 rule config 发给模型或 preview。
- 不让未绑定商品回退到 Passistant。
- 不继续从 `custom_prompts`、`max_discount_*`、`max_bargain_rounds` 驱动商品业务。
- 不创建第二件 Passistant 商品，不改商品/card/delivery/真实消息。
- 不读写 Passistant 上游仓库，不引入向量/embedding/远程知识服务。
- 不 push、发 PR、改 remote 或提交秘密/运行 DB。
