# 架构设计

[返回 README](./README.md) · [上一篇：执行文档](./00-执行文档.md) · [下一篇：开发规范](./02-开发规范.md)

## 1. 设计结论

采用“全局知识库资源 + 商品多对多绑定 + 四类内容 + 结构化业务规则 + 单例全局回复风格”的模型。

核心边界：

- 知识库是全局的，不属于账号或用户；
- 商品只保存绑定，不复制知识内容；
- 商品业务由绑定知识库提供；
- 全局回复风格只控制表达方式；
- 订单事实、身份认证和秘密泄露防护仍由引擎/路由硬编码保护。

这能同时解决幽灵 Passistant、重复数据、错误商品污染、无法维护来源/内部规则和全局 prompt 混入商品业务五类问题。

## 2. 当前架构与根因

### 2.1 当前数据流

```text
选择账号 + 商品
      │
      ▼
GET /items/{cookie}/{item}/ai-knowledge
      │
      ├─ documents(cookie_id,item_id)  一件商品一份文档
      └─ entries(cookie_id,item_id)    每件商品复制全部条目

AIReplyEngine
      ├─ 账号 custom_prompts（风格 + Passistant 业务混合）
      ├─ 账号 max_discount_* / max_bargain_rounds
      └─ ProductKnowledgeService（全局 Passistant 策略先于绑定检查）
```

### 2.2 根因

1. `ai_product_knowledge_documents` 的主键就是商品 scope，不存在独立知识库实体。
2. `get_product_knowledge_document` 在查无数据时仍返回 `passistant`，UI 因而无法区分“空”与“Passistant”。
3. `source_refs` 被 API 删除，内部规则根本没有持久化/管理模型。
4. Passistant 固定回复和输出词表是 `product_knowledge.py` 的模块级常量，对所有商品先行分类。
5. `_resolve_system_prompt` 对解析失败的 JSON 直接按纯文本使用；当前旧 prompt 因格式无效而成为所有意图的通用业务 prompt。
6. 议价字段仍在账号 AI settings，无法表达不同商品/知识库的不同商业边界。

## 3. 目标组件与数据流

```text
                         ┌───────────────────────────────┐
                         │ 全局 AI Reply Profile         │
                         │ reply_style（只含语气）       │
                         └──────────────┬────────────────┘
                                        │
商品(cookie_id,item_id) ─ bindings ─ 全局知识库（0..N）
                                        │
                         ┌──────────────┼───────────────┐
                         │              │               │
                       facts          rules            qa
                         │              │               │
                         └──── source_refs（管理审计） ─┘
                                        │
                                        ▼
                         KnowledgeRuntimeSnapshot
                         facts + qa + executable rules
                                        │
系统/订单/secret guard ─────────────────┤
                                        ▼
规则前置分流 → 检索 → style + facts/qa → 模型 → 输出 guard
```

管理端读取完整知识库，包括 sources 和 rules。运行端使用专门的 snapshot DTO：只把启用的 buyer facts/qa answer 交给模型，sources 永不进入 snapshot 的模型字段。

## 4. 数据模型

### 4.1 `ai_knowledge_bases`

| 字段 | 语义 |
| --- | --- |
| `id TEXT PRIMARY KEY` | 服务端生成 UUID，不因改名改变 |
| `base_key TEXT UNIQUE NOT NULL` | 稳定小写 key；内置库为 `passistant` |
| `name TEXT UNIQUE NOT NULL` | 展示名；初始为 `Passistant` |
| `description TEXT NOT NULL DEFAULT ''` | 管理摘要 |
| `version INTEGER NOT NULL DEFAULT 1` | 任意元数据/内容 mutation 后递增 |
| `enabled BOOLEAN NOT NULL DEFAULT TRUE` | 停用后所有绑定暂不参与运行时 |
| `schema_version INTEGER NOT NULL DEFAULT 2` | 内容合同版本 |
| `seed_version/checksum` | 内置迁移来源与规范化摘要 |
| `created_at/updated_at` | 审计时间 |

不包含 `user_id`、`cookie_id`、owner、visibility 或 role。

### 4.2 `ai_knowledge_facts`

买家可见、可直接作为模型事实的数据，例如产品身份、支持区服、30 天权益。

| 字段 | 语义 |
| --- | --- |
| `id` / `knowledge_base_id` | UUID 与所属全局库 |
| `fact_key` | 库内唯一稳定 key |
| `category` / `title` | 分类与管理标题 |
| `content` | 买家可见事实纯文本 |
| `source_ids` | 同库 source UUID JSON 数组 |
| `priority` / `enabled` | 检索与运行开关 |

### 4.3 `ai_knowledge_sources`

管理侧来源审计，既可以是文档章节，也可以是用户确认的业务事实。

| 字段 | 语义 |
| --- | --- |
| `id` / `knowledge_base_id` | UUID 与所属库 |
| `source_key` | 库内唯一 key |
| `title` | 可读标题 |
| `reference` | 文档名/章节或批准记录；纯文本 |
| `url` | 可选 HTTP(S) 公开链接；本地绝对路径禁止通过 API 返回 |
| `notes` | 管理备注，不入模型 |

删除被 fact/qa/rule 引用的 source 默认返回 409。调用者必须先解除引用，不能静默留下悬空 source id。

### 4.4 `ai_knowledge_rules`

内部业务规则，不直接展示给买家。固定/价格类由服务端解释，模型 instruction 只是补充且永远低于引擎硬安全。

| 字段 | 语义 |
| --- | --- |
| `id` / `knowledge_base_id` | UUID 与所属库 |
| `rule_key` | 库内唯一稳定 key |
| `name` | 管理标题 |
| `rule_type` | 受限枚举，见下文 |
| `intent` | `safety/commercial_sensitive/pricing/bargain/general/...` |
| `matchers` | 服务端校验的短语/正则定义 JSON |
| `instruction` | 模型可见内部业务指令；仅 `model_instruction` 使用 |
| `response` | 固定回复；仅固定规则使用 |
| `config_json` | 对应类型的受限结构 |
| `source_ids` | 审计来源，不入模型 |
| `priority` / `enabled` | 冲突选择与开关 |

首版 `rule_type`：

- `fixed_reply`：命中 matcher 后服务端直接回复，零模型调用；
- `topic_refusal`：商业敏感类固定拒答，零模型调用；
- `pricing_policy`：原价、当前价、活动文案和允许折扣边界；
- `bargain_policy`：最大折扣比例/金额/轮次及最低价策略；
- `model_instruction`：仅向模型提供当前商品业务说明；
- `output_guard`：未问不主动提及、禁止输出规则等后置约束。

`rule_type` 不允许前端任意创建可执行代码或 SQL。`config_json` 必须按 discriminator 由 Pydantic/领域服务验证，未知字段拒绝。

### 4.5 `ai_knowledge_qa_entries`

| 字段 | 语义 |
| --- | --- |
| `id` / `knowledge_base_id` | UUID 与所属库 |
| `qa_key` | 库内唯一稳定 key |
| `category` | 公开问答分类 |
| `questions` | 常见完整问法数组 |
| `keywords` | 确定性检索词数组 |
| `answer` | 买家可见公开答案 |
| `source_ids` | 同库来源引用 |
| `priority` / `enabled` | 排序与开关 |

现有 20 个 `entries` 迁为公开问答；其中可复用的陈述同时形成 facts 时，运行时去重，不能把同一句重复注入模型。

### 4.6 `ai_item_knowledge_bindings`

```sql
PRIMARY KEY (cookie_id, item_id, knowledge_base_id)
UNIQUE (cookie_id, item_id, sort_order)
FOREIGN KEY (cookie_id, item_id) REFERENCES item_info(...)
FOREIGN KEY (knowledge_base_id) REFERENCES ai_knowledge_bases(id)
```

字段包含 `sort_order` 和 `created_at`。绑定没有 owner；访问绑定 API 时，route 仍验证调用者能访问该 cookie/item。删除 item 或 base 必须级联/显式清理 binding，兼容未启用 SQLite foreign keys 的历史连接。

### 4.7 `ai_reply_profile`

单例行 `profile_key='default'`：`reply_style`、`version`、时间戳。它与账号 `ai_reply_settings` 分离。

### 4.8 `ai_knowledge_migrations`

保存 `migration_key`、`applied_at`、`details_checksum`。关键迁移 key 为 `global-knowledge-v2-passistant-20260907`。marker 必须与新数据在同一事务提交，避免半迁移；用户以后删除 Passistant 时不能因重启再次自动创建。

## 5. 聚合与版本合同

- knowledge base `version` 是整个聚合的乐观锁：元数据、fact、source、rule、qa 任一 mutation 都要求 `expected_version` 并递增一次。
- list/read 不修改 version；preview 不修改任何数据。
- create 初始 version 1；同一 mutation 的客户端重试若首轮已成功，第二次返回 409 和 current version 摘要。
- 内容 id 由服务端生成；stable key 库内唯一。重命名 title/name 不改变 id。
- checksum 基于规范化 base 元数据与四类内容，按 type/key 排序；不含 id、timestamp、binding 和 source 本地路径。
- 添加/删除 binding 不改变 base version；binding 本身由唯一约束和返回状态保证一致。

## 6. API 合同

所有路由继续要求现有 `get_current_user`。全局库只检查“已登录”，商品 binding 额外检查 cookie/item scope。

### 6.1 全局库

| Method | Path | 行为 |
| --- | --- | --- |
| GET | `/knowledge-bases` | 返回 summary 列表、四类计数和 `binding_count` |
| POST | `/knowledge-bases` | 只接收 name/description；服务端生成 custom base_key；name 冲突 409 |
| GET | `/knowledge-bases/{base_id}` | 返回元数据与四类完整管理内容 |
| PUT | `/knowledge-bases/{base_id}` | 修改 name/description/enabled，携带 expected_version |
| DELETE | `/knowledge-bases/{base_id}` | 携带 expected_version；事务级联内容/bindings，返回 binding_count |

创建请求不接受 owner/user/cookie 字段。删除响应只返回 id/name/deleted/binding_count，不回显全部内容。

### 6.2 内容 CRUD

为四种资源提供固定的单资源 CRUD 合同：

```text
POST   /knowledge-bases/{base_id}/facts
PUT    /knowledge-bases/{base_id}/facts/{content_id}
DELETE /knowledge-bases/{base_id}/facts/{content_id}?expected_version=N
POST   /knowledge-bases/{base_id}/sources
PUT    /knowledge-bases/{base_id}/sources/{content_id}
DELETE /knowledge-bases/{base_id}/sources/{content_id}?expected_version=N
POST   /knowledge-bases/{base_id}/rules
PUT    /knowledge-bases/{base_id}/rules/{content_id}
DELETE /knowledge-bases/{base_id}/rules/{content_id}?expected_version=N
POST   /knowledge-bases/{base_id}/qa-entries
PUT    /knowledge-bases/{base_id}/qa-entries/{content_id}
DELETE /knowledge-bases/{base_id}/qa-entries/{content_id}?expected_version=N
```

POST/PUT body 都包含 `expected_version`；DELETE 固定使用 query 参数。响应返回更新后的 base version 和目标资源。编辑器每次只保存一个资源，成功后 GET 聚合；不存在批量 `/contents` 写路径，避免多步局部成功被误认为一次原子保存。

### 6.3 商品绑定

| Method | Path | 行为 |
| --- | --- | --- |
| GET | `/items/{cookie_id}/{item_id}/knowledge-bindings` | 当前商品真实绑定列表 |
| POST | `/items/{cookie_id}/{item_id}/knowledge-bindings` | `{knowledge_base_id}`；重复 409 |
| DELETE | `/items/{cookie_id}/{item_id}/knowledge-bindings/{base_id}` | 仅解绑；不存在固定返回 404 |

本计划选择 DELETE 不存在返回 404，使错误选择可见；客户端只在当前 GET 返回的 binding 上展示删除候选。

### 6.4 Preview

`POST /items/{cookie_id}/{item_id}/knowledge-preview` 接收 1～500 字符 message，返回命中的 `base_key/content_key/category/score`、策略类型和固定回复预览。它不调用模型、不保存会话、不返回 sources/internal instruction/config。

### 6.5 全局回复风格

| Method | Path | 行为 |
| --- | --- | --- |
| GET | `/ai-reply-style` | 返回 default profile 的 style/version |
| PUT | `/ai-reply-style` | `{expected_version, reply_style}`；冲突 409 |

账号 `/ai-reply-settings/{cookie_id}` 继续管理启用、模型、API、UA 和上下文。旧 prompt/议价字段保留在 DB 一个发布周期，但从新 response/request 和运行时移除；账号设置保存改为活动字段 UPDATE/upsert，不能用缺字段的 `INSERT OR REPLACE` 重置 API key、上下文或旧列。

## 7. Passistant 内容迁移

### 7.1 旧 prompt 业务映射

| 旧内容类别 | 新归属 | 说明 |
| --- | --- | --- |
| “回复俏皮/简洁/像卖家” | 全局 `reply_style` | 只保留语气，不保留商品名 |
| Passistant 产品身份 | fact + public qa | 只在绑定商品生效 |
| 30 天权益/一次性激活码 | fact + public qa | 来源可审计 |
| 原价 29.9、当前活动 9.9 | pricing rule + qa | 结构化金额与公开口径 |
| 不额外砍价、折扣/轮次 | bargain rule | 从账号 settings 迁出 |
| 国际服/台服、国服不支持 | fact + qa | 商品业务 |
| 安装、启动、激活 | fact + qa | 商品业务 |
| 自动交付说明 | fact/qa | 只说明交付方式，不宣称具体订单已发货 |
| 安全/封号固定句 | fixed_reply rule | 绑定后零模型调用 |
| 源码/成本等拒答 | topic_refusal rule | 绑定后零模型调用；secret 硬防护仍全局 |
| 未问不主动谈安全 | output_guard rule | 绑定后执行 |
| 不虚构付款/发货/退款状态 | 引擎级硬规则 | 不能迁成可删除业务规则 |

旧 `custom_prompts` 无效 JSON 不作为迁移源。迁移仅使用已经审计的 seed、本表映射和用户确认的回复风格，避免把语法错误、过期价格或未知片段带入新系统。

### 7.2 数据选择

当前两份旧文档 checksum 相同，因此只生成一个全局 Passistant。绑定选择不按“第一条”或 checksum 猜测，而按已确认的产品 item `1081710901648`；iPhone `741903197018` 明确排除。

迁移前若商品不存在或标题证据不再匹配，事务不写 marker并报错；执行者必须更新事实证据，不能退化为绑定所有旧文档。

## 8. AI 运行时

### 8.1 时序

```text
AI enabled / 系统订单事件检查
  → 最新消息防抖
  → 加载全局 reply_style
  → load_snapshot(cookie,item)
       ├─ 无 binding：空商品规则/知识
       └─ 有 binding：启用 bases 的 facts/qa/rules
  → 引擎级输入硬防护
  → 绑定库 fixed/topic rules
  → pricing/bargain rules
  → facts/qa 确定性检索
  → 组装 style + 商品事实 + 内部 instruction
  → 模型调用
  → normalize
  → 引擎级输出硬防护
  → 绑定库 output guard / pricing validation
  → 保存最终回复
```

### 8.2 多库合并

- 内容排序：`score DESC, content_priority DESC, binding_sort_order ASC, base_key ASC, content_key ASC`。
- 去重：规范化后的相同公开 content/answer 只注入一次。
- 固定规则：`rule_priority DESC` 后按 binding/key 确定选择；同优先级不同 response 记录 warning，不随机选择。
- 价格规则：取最高最低价、最小允许折扣、最小可用议价轮次，即最严格可行边界；若币种/商品口径冲突，fail closed 为不议价并转人工确认，不让模型自行折中。
- instruction：按绑定顺序追加，每库/总量均有字符预算；不得覆盖硬安全或其他结构化 rule。
- 删除/解绑后下一请求立即生效；首版不做跨请求缓存。如未来缓存，key 必须包含 item binding fingerprint 和所有 base versions。

## 9. 页面交互

### 9.1 当前项目知识库

- 账号和商品仍用于选择当前项目 scope；知识库本身不归账号。
- 列表只来自 bindings GET；空态不创建默认文档。
- “添加知识库”打开全局列表。已绑定项可显示但禁用，标签“已添加”；服务端 409 处理并刷新。
- “删除知识库”打开已绑定列表；确认文案明确是解绑，不删除全局内容。

### 9.2 全部知识库

- header 右侧“添加知识库”创建空库。
- row 主体点击打开编辑器；行尾 delete 使用独立按钮、`stopPropagation`。
- 删除确认显示 `name + binding_count`，说明四类内容和全部商品绑定将被删除；确认后调用全局 DELETE。
- Passistant 不是不可删除的特殊 UI 项；迁移 marker 保证删除后不会被启动自动恢复。

### 9.3 编辑器

四个 tab/section：买家可见事实、来源引用、内部规则、公开问答。每项有明确新增、编辑、删除、启用和保存。来源选择通过同库 source id 多选，不能手填跨库 id。

未保存状态关闭/切库要确认。version 409 不自动覆盖，而是提示重新加载；创建/删除提交中禁用按钮。编辑器用纯文本控件，不使用 `dangerouslySetInnerHTML`。

## 10. 安全与权限边界

- 全局可用表示不做知识库 owner 校验，不表示取消应用认证。
- binding route 先验证当前用户拥有 cookie，再验证 item；非所属 cookie 不泄露 item 是否存在。
- source reference 的本地路径/notes 只用于管理 API；运行 snapshot 和 preview response 做独立白名单序列化。
- rule config 不允许表达代码、模板执行、URL 请求、SQL 或文件路径。
- 管理输入全部按纯文本保存和渲染；URL 仅允许 `http/https`，不抓取。
- 通用 admin data table 白名单不得加入新知识表，避免绕过 version、引用和迁移约束。
- 日志只记 base/rule/content key、version、数量和错误代码；不记完整 prompt、answer、source notes 或买家消息。

## 11. 失败与恢复

| 故障 | 行为 | 恢复 |
| --- | --- | --- |
| duplicate binding | 409，无重复行 | 前端刷新 bindings，显示已添加 |
| stale base version | 409，无部分内容写入 | GET 最新聚合，人工合并 |
| 删除被引用 source | 409，列出引用计数而非内容 | 先解除引用再删 |
| 全局删除中途失败 | 单事务 rollback | GET 确认库和 bindings 均仍存在 |
| 迁移中途失败 | marker 与新数据全部 rollback | 修复后安全重试 |
| 迁移重复运行 | marker 命中，no-op | 记录 already_applied |
| 用户删除 Passistant 后重启 | marker 保留，不重建 | 用户可从 UI 手动创建/导入 |
| 规则 JSON 损坏 | 保存时 422；运行时 fail closed | 禁用异常规则、记录 key，人工修复 |
| 多库价格冲突 | 不议价/人工确认 | 使用者调整绑定或规则优先级 |
| style 无法读取 | 使用代码内纯风格安全默认值 | 修复 profile 后回读 |

## 12. 迁移、发布与回滚

1. 新表和 marker 使用幂等 DDL。
2. 在同一事务创建 Passistant base、sources/facts/rules/qa、唯一正确 binding、reply profile 和 marker。
3. 新运行时切到新表；旧两张商品知识表只读保留一个发布周期。
4. 新前端/API 发布后，旧四个 `/ai-knowledge...` 路由固定返回 410 和新路径提示；不做旧表读取、兼容写或双写。
5. 验收正确商品与普通商品零污染，再考虑后续独立清理旧表/旧 settings 列；本计划不 DROP。

应用回滚时，新表可以保留，旧版本仍能读取旧表。数据回滚优先恢复 P5.1 的 SQLite online backup，不运行手写逆向 DELETE。若只需停用新能力，可停用 bases 或解绑，而不删除内容。引擎级安全规则不得作为回滚项关闭。

## 13. 关键决策与未选方案

| 决策 | 采用 | 未采用 | 原因 |
| --- | --- | --- | --- |
| 所属关系 | 全局 base + 商品 binding | 按账号/商品复制 | 满足复用与空商品语义 |
| 内容模型 | facts/sources/rules/qa 分表 | 单个万能 JSON blob | CRUD、引用完整性和规则校验更清楚 |
| 并发 | 聚合 version | last-write-wins | 防止多个编辑窗口静默覆盖 |
| 权限 | 现有登录 + 商品 scope | owner/admin/RBAC | 用户明确单人使用且不需要权限控制 |
| 回复风格 | 全局 singleton | 账号 custom prompt | 用户要求整个 AI 的统一风格 |
| 商品规则 | 结构化知识库 rule | 自由 prompt | 只对绑定商品生效且可测试 |
| 多库冲突 | 稳定排序 + 最严格价格 | 让 LLM 决定 | 可预测、可审计 |
| 迁移 | marker + 精确 item | 扫描所有旧文档自动绑定 | 防止 iPhone 等错误商品继续污染 |
| 删除 | 全局级联 bindings | 拒绝删除已绑定库 | 用户明确要求确认后删除；警示影响即可 |
| 检索 | 本地确定性 | 向量/embedding | 当前规模小，无新隐私与部署成本 |
