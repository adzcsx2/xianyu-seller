# 开发规范

[返回 README](./README.md) · [上一篇：架构设计](./01-架构设计.md) · [下一篇：修复路线图](./03-修复路线图.md)

## 1. 适用范围与优先级

本规范适用于本计划新增或修改的 Python/FastAPI/SQLite/React/TypeScript 代码。优先级为：用户明确要求 → `AGENT.md`/`CLAUDE.md` → `docs/references/ai-rules` → 本规范 → 周边代码风格。

若实际源码与计划定位不同，执行代理必须先在 P<N>.1 记录稳定符号和调用者，再调整插入点；不得为了匹配计划而复制旧逻辑或创建第二事实源。

## 3. 功能开关注册表合同

### 3.1 定义结构

```python
@dataclass(frozen=True)
class FeatureFlagDefinition:
    key: str
    default: bool
    group: str
    label: str
    description: str
    depends_on: tuple[str, ...] = ()
    ui_targets: tuple[str, ...] = ()
    risk_level: str = "low"
```

要求：

- registry 使用不可变有序集合，API 和测试顺序稳定；
- key 采用 `snake_case`，现有 key 不重命名；
- 所有值必须是 Boolean，interval/template 不得混入；
- `depends_on` 只能引用已定义 key，启动时检测未知依赖和环；
- `ui_targets` 使用 Sidebar page ID 或稳定 control ID；纯后台开关为空数组；
- label/description 可返回前端，但不能包含秘密或运行数据。

### 3.2 严格解析

数据库兼容读取可接受 `true/false/1/0`，并规范为 Boolean。HTTP 请求只接受 JSON `true/false`；Python 的 `bool` 必须显式校验，不能让 `1`、`"false"` 或任意 truthy 值通过。

```python
if type(value) is not bool:
    raise InvalidFeatureFlag(key)
```

禁止使用 `bool(value)` 解析字符串，因为 `bool("false") is True`。

### 3.3 effective 计算

```python
effective[key] = configured[key] and all(effective[parent] for parent in depends_on)
```

使用拓扑顺序计算；configured 永不因依赖失败而变化。snapshot 必须同时包含完整 configured/effective，不允许客户端自己推导后端门禁。

## 4. 数据库与事务

### 4.1 缺键迁移

- 只用 `INSERT OR IGNORE`；
- 已存在值逐字保留；
- 新 key 的 default 来自 registry；
- `feature_flags_revision` 是整数设置，初始 `0`；
- 初始化二次执行无变化；
- 不删除历史环境变量或 system setting，弃用只通过文档和读取优先级完成。

### 4.2 原子更新模板

```python
def update_feature_flags_atomic(self, patch: dict[str, bool], expected_revision: int):
    validated = registry.validate_patch(patch)
    with self.lock:
        cursor = self.conn.cursor()
        try:
            cursor.execute("BEGIN IMMEDIATE")
            current = self._read_feature_snapshot(cursor)
            if current.revision != expected_revision:
                raise FeatureRevisionConflict(...)
            for key, value in validated.items():
                self._set_system_setting_with_cursor(cursor, key, "true" if value else "false")
            self._set_revision_with_cursor(cursor, current.revision + 1)
            self.conn.commit()
        except Exception:
            self.conn.rollback()
            raise
    return self.get_feature_flags()
```

具体 SQL 复用现有 helper；禁止调用会自行 commit 的 `set_system_setting` 破坏事务。测试必须注入中途异常证明整批 rollback。

### 4.3 数据保护

禁止在 feature 更新事务中执行：

- `UPDATE cookies SET auto_*`；
- 删除商品/订单/卡密/知识库；
- 清空模板或 interval；
- 自动修改依赖子 key；
- 读取或记录 Cookie/Token/聊天正文。

## 5. API 规范

### 5.1 认证与输入

- `GET /feature-flags` 使用现有 `get_current_user`，仅返回非敏感可见性合同；`PUT /feature-flags` 使用 `require_admin`；
- Pydantic 模型禁止 extra fields，Boolean 使用 strict 模式；
- patch 至少含一个 key；未知 key 返回 422；
- PUT 必须携带 `expected_revision`；
- 响应只返回 feature 合同，不混入全部系统设置。

### 5.2 错误映射

| 领域异常 | HTTP | code |
| --- | ---: | --- |
| `InvalidFeatureFlag` | 422 | `invalid_feature_flag` |
| `FeatureRevisionConflict` | 409 | `feature_revision_conflict` |
| `FeatureDisabled` | 409 | `feature_disabled` |
| 未知事务错误 | 500 | `feature_flags_update_failed` |

错误消息不能包含 SQL、数据库路径、Cookie、Token 或堆栈。详细异常只进入服务端脱敏日志。

### 5.3 门禁模板

```python
def require_feature(key: str) -> None:
    snapshot = db_manager.get_feature_flags()
    if not snapshot.effective[key]:
        raise HTTPException(
            status_code=409,
            detail={
                "code": "feature_disabled",
                "feature": key,
                "message": "功能已关闭，请到系统设置 > 功能区开启",
            },
        )
```

门禁必须位于 route 的第一个业务副作用之前。是否门禁 GET 读取由架构矩阵决定：恢复配置所需 GET 保留，mutation 和主动平台请求必须门禁。

## 6. asyncio 与跨线程规范

### 6.1 task 表

每个可选 task 有唯一属性名、factory 和 feature key：

```python
OPTIONAL_TASKS = {
    "scheduled_token_refresh_enabled": ("token_refresh_task", "token_refresh_loop"),
    "browser_cookie_refresh_enabled": ("cookie_refresh_task", "cookie_refresh_loop"),
    # ...
}
```

实际实现可用结构体，但不得在 `main` 复制八段不同判断。核心 heartbeat 和 local cleanup 不进入此表。

### 6.2 启停规则

- start：只有 effective=true 且 task 不存在或 done 时创建；
- stop：先 cancel，再有限时 await，吞掉预期 `CancelledError`，最后设引用为 `None`；
- loop：每次外部调用前再次读取 effective；
- reconnect：调用同一 reconcile，不复制启动逻辑；
- shutdown：沿用现有统一清理，新增 task 必须进入可取消集合；
- one-shot profile sync：用 tracked task，并在关闭时取消未完成任务。

不得跨事件循环直接 await/cancel。`CookieManager.apply_feature_flags` 复用 `run_coroutine_threadsafe`，设置有限超时并返回逐实例状态。

### 6.3 消息事件门禁

在 `handle_message` 中按以下顺序：

1. 解密/解析消息并维持聊天接收；
2. 若订单模块 effective=false，跳过订单 ID 预取、成交值、详情和状态写入；
3. 若自动发货=false，付款和免拼分支只记录一次 debug 后返回/继续，不调用详情或发货；
4. 若买家互动=false，收货系统消息不致谢、不调度互动；
5. 系统消息仍不得落入普通自动回复；
6. 若自动回复=false，不创建 debounce reply task；
7. 手动聊天、通知展示和会话读取继续。

门禁应调用统一 helper，禁止散落 `db_manager.get_system_setting(...) == 'true'`。

## 7. 前端保存与交互规范

### 7.1 类型

`FeatureKey` 使用字符串联合类型，key 列表由 `as const` 生成。禁止把 feature 放进 `SystemSettings` 的 `[key: string]: any` 后继续弱类型访问。

```ts
export interface FeatureFlagSnapshot {
  revision: number;
  configured: Record<FeatureKey, boolean>;
  effective: Record<FeatureKey, boolean>;
  definitions: FeatureFlagDefinition[];
  warnings: string[];
}
```

### 7.2 状态分层

- `snapshot`：服务端已保存状态，Context 全局共享；
- `draft`：Settings 功能区本地编辑；
- `saving`：阻止重复请求；
- `loadError/saveError`：明确展示；
- 仅 PUT 成功 response 能替换 snapshot。

保存失败时不广播、不隐藏页面、不覆盖 localStorage。409 时提示并重新加载；不得静默 last-write-wins。

### 7.3 功能区

- 新 tab ID 为 `features`，label 为“功能区”；
- 分组顺序固定：页面模块 → 平台主动任务 → 消息动作；
- 每个 switch 有 title、description、risk/dependency 状态；
- 父依赖关闭时允许查看和编辑 configured 子值，但明确显示“当前不生效”；
- 买家互动说明必须包含“不会修改各账号的自动评价、求花和确认收货致谢设置”；
- interval 只在对应 configured=true 时显示，关闭不清空值。

### 7.4 页面隐藏

- Sidebar 过滤 menu item，并过滤空 group；
- App 不 mount 禁用页面，不能仅使用 `hidden`；
- `active_page` 无效时回退 messages，再写回 localStorage；
- snapshot 加载中不渲染可选页面，避免闪现；
- Settings、messages、accounts、dashboard、notifications、about 始终可达。

## 8. 测试规范

- 先写语义红灯，再实现；红灯不能是 import/语法/fixture 错误。
- DB 测试全部使用 `tempfile.TemporaryDirectory` 和独立 SQLite。
- 运行时测试 mock `refresh_token`、卖家 API、订单详情、发货、评价/求花、`send_msg`，断言关闭时 call count 为 0。
- task 测试使用 `IsolatedAsyncioTestCase`，tearDown 必须 cancel/gather，不能泄漏任务。
- API 测试覆盖管理员/非管理员、strict bool、unknown key、revision 冲突、rollback 和稳定错误。
- 前端无现成 JS test runner：先沿用 Python 静态合同确保 key/入口，再用生产 build 和本地浏览器验收补足动态交互；不为本需求单独引入大型测试依赖。
- 每个 REQ 至少关联一个自动测试或明确人工 E2E；高风险门禁必须有自动测试。
- 使用 `python scripts/run_tests.py --suite all --coverage --quality --database snapshot` 做最终门禁。

## 9. 日志与可观测性

允许记录：

```text
feature_flags revision=4 changed=[order_sync_enabled] runtime_apply=applied
account=<masked> task=order_sync action=cancelled
feature=auto_delivery_enabled blocked source=message_event
```

禁止记录：请求 payload 全文、Cookie、Token、验证码链接、订单/聊天正文、卡密或环境变量值。对同一关闭事件做采样/debug，避免每条消息刷 warning。

## 10. 变更与 Git 纪律

- 修改前后运行 `git status --short`；
- 对 `app/reply_server.py`、`frontend/services/api.ts`、`frontend/components/AccountList.tsx` 和 `utils/xianyu_slider_stealth.py` 逐 hunk 审计；
- 不使用 `git reset --hard`、`git checkout --` 或整文件替换；
- 不提交 `data/`、`logs/`、`.env`、浏览器数据或临时 API index；
- API 索引只在 Phase 4 代码稳定后正式重建；
- 品牌迁移只在 Phase 1～4 全绿后执行，根 README 必须是 P5 的最后一个内容改动；
- 每个 Phase 结束运行 `git diff --check`。

## 11. 禁止模式

- `bool(db_value)`、`settings[key] !== false` 作为无合同默认；
- 多处复制 feature key 字符串和默认值；
- `Promise.all` 逐项保存功能开关；
- 保存请求发出前就隐藏页面；
- 父模块关闭时把所有子开关写 false；
- 只取消 task，不在副作用前二次门禁；
- 只门禁后台 loop，漏掉消息触发或直接 API；
- 把周期 Token 关闭解释为永不刷新 Token；
- 把“目标请求为零”宣传为“不会出现滑块”。

## 12. 品牌、外链与 README 规范

### 12.1 命名合同

- 用户可见名称只能是“闲鱼卖家”，不得保留旧中文名或旧英文口号；
- 第一方 slug 只能是 `xianyu-seller`，应用到 npm 包、app-shell、镜像、容器、Worker 和自定义 User-Agent；
- 第一方仓库链接统一为 `https://github.com/adzcsx2/xianyu-seller`，GHCR 固定为 `ghcr.io/adzcsx2/xianyu-seller:latest`；
- Docker `maintainer` / `author` 和其他第一方作者字段统一为 `adzcsx2`；
- About 没有新官网和邮箱时直接移除相应卡片，不能显示旧地址、空链接或虚构联系方式。

建立 `tests/test_brand_identity.py` 作为静态合同。旧字符串常量必须由分段字面量拼接，避免测试自身成为残留；测试扫描 tracked 第一方文本、HTML 和生成后的静态壳，且只允许根 README 的唯一 fork 声明命中直接上游身份。

### 12.2 外部服务迁移

旧维护者服务 URL 采用精确值匹配，禁止 `contains`、域名模糊匹配或清空任意 URL：

```python
if current_url == LEGACY_DEFAULT_URL:
    save_url("")
    save_enabled(False)
else:
    preserve(current_url)
```

- 新安装默认 URL 为空并默认禁用；空值不能发 HTTP 请求；
- 现有值等于已冻结旧默认时迁移为空/禁用；用户自定义值逐字保留；
- 页面将空值解释为“未配置”，不得 fallback 到旧常量；
- 迁移日志只记 setting key 和动作，不打印完整 URL、API key 或用户数据；
- 公告、AI、商品详情分别测试，不能用一个通用迁移误伤其他设置。

### 12.3 分发与构建产物

- 修改 `frontend/package.json` 后，以最小补丁同步 lockfile 顶层和根 package 的两个 `name` 字段；不得为品牌改名重新解析依赖，依赖作者和 sponsor URL 不修改；
- `frontend/index.html` 是源，`static/index.html` 和 `static/assets/` 只在 P5.5 由 `npm --prefix frontend run build` 重建一次；禁止手改压缩 bundle，README 重写后不得再运行会改写 `static/` 的生产构建；
- Compose 服务名 `xianyu-app` 可保留为内部稳定键，但 image/container/network 中的第一方品牌改为新 slug；
- NAS 镜像必须指向目标 GHCR；两个 Dockerfile 的 repository/author/maintainer 一致；
- 删除旧 fork 统计资产前先用 `rg` 确认只被对应统计脚本/工作流和旧 README 引用，删除后再次确认零悬挂引用；
- 历史计划中的机器绝对路径改为 `<repo-root>`，不自动移动本机目录。

### 12.4 根 README 重写合同

README 最后重写，至少包含：

1. “闲鱼卖家”标题和一段准确定位；
2. 唯一一条直接上游 fork 声明；
3. 基于最终代码的功能概览与功能区/聊天模式说明；
4. 指向目标仓库的 clone、release、issue 与镜像信息；
5. Docker、NAS、源码运行、升级迁移和数据备份步骤；
6. 登录安全、Cookie/Token/卡密/聊天数据保护与风控边界；
7. 公告、AI、商品详情服务需要自行显式配置的说明；
8. 测试、许可证和贡献入口。

不得出现上游徽章、fork 网络星标图、旧作者简介、旧官网/邮箱、更早来源链或“零风控”承诺。README 中直接上游身份的允许次数为一行一次；同一身份不得在 badge、脚注和其他章节重复。

### 12.5 零残留命令

执行代理先由 P5.1 固化旧 token 清单，最终使用分段字符串构造扫描，避免计划或测试代码自身命中：

```powershell
$legacy = @(
  ('闲鱼' + '超级管家'),
  ('闲鱼' + '智控'),
  ('XIANYU SUPER ' + 'BUTLER'),
  ('xianyu-super-' + 'butler'),
  ('23' + 'Star'),
  ('zhinian' + 'boke'),
  ('cor' + 'leom')
)
git grep -n -I -E ($legacy -join '|') -- . ':(exclude)LICENSE' ':(exclude)frontend/package-lock.json'
```

绿色结果只能是根 README 的唯一 fork 声明。随后单独断言：

- 不含直接上游身份的旧名称、旧维护者域名/邮箱、旧二级来源或旧机器 slug 为 0；
- 直接上游 owner/repository 组合恰好命中根 README 一行；
- `git grep` 目标产品名、目标仓库、目标镜像和目标 author 均命中预期文件；
- package-lock 中第三方作者/赞助链接不参与替换，但其根项目名必须是新 slug。
