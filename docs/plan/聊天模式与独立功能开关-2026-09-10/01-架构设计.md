# 架构设计

[返回 README](./README.md) · [上一篇：执行文档](./00-执行文档.md) · [下一篇：开发规范](./02-开发规范.md)

## 1. 设计结论

采用“现有 `system_settings` 持久化 + 后端强类型注册表 + configured/effective 双状态 + 跨线程任务收敛 + 前端共享 snapshot”的架构。

核心原则：

- 数据库保存用户配置，注册表定义合法 key、默认值、依赖、运行门禁和 UI 目标；
- configured 是用户保存值，effective 是叠加父依赖后的实际值；
- 关闭父模块不覆写子配置，保证以后重新开启时恢复原样；
- 后端门禁先于任何平台请求，前端隐藏只是相同状态的展示；
- 周期 Token 刷新与连接所需 Token 获取分离，关闭前者不破坏聊天；
- 账号级评价/求花/致谢继续留在 `cookies` 表，不被系统级总开关迁移或清零。
- 品牌迁移最后执行，以一组固定身份值覆盖界面、包、容器和发布元数据；旧维护者服务没有新地址时改为未配置，而不是换成猜测域名。

## 2. 当前问题与风险来源

### 2.1 当前连接后行为

```text
XianyuLive.main 建立 WebSocket
  ├─ init -> Token 缺失或超过 3600 秒时 refresh_token
  ├─ heartbeat_loop                         聊天核心
  ├─ token_refresh_loop                     主动 MTOP，请求后断线重连
  ├─ pause_cleanup_loop                     本地维护
  ├─ cookie_refresh_loop                    浏览器刷新，当前约 1200 秒
  ├─ item_sync_loop                         商品接口
  ├─ order_sync_loop                        卖家订单接口
  ├─ _sync_account_profile                  连接后一次主动资料请求
  ├─ item_polish_loop                       擦亮接口
  ├─ delivery_timeout_loop                  卖家订单接口
  └─ buyer_interaction_loop                 订单、评价、求花接口

收到消息 -> handle_message
  ├─ 先提取订单 ID
  ├─ 先查真实成交数据和订单详情
  ├─ 再处理自动发货/免拼/收货互动
  └─ 最后调度普通自动回复
```

因此，只隐藏订单/商品页面或不点击按钮不能停止后台请求。`AUTO_DELIVERY_ENABLED` 和 `AUTO_REPLY_ENABLED` 虽出现在环境示例与 Compose 中，但当前源码没有把它们作为统一运行门禁；它们不能证明功能已关闭。

### 2.2 滑块结论边界

滑块由平台风险判断触发，不能从本地代码证明唯一原因。下列行为会增加主动请求面：

- 每小时 Token MTOP 请求和刷新成功后的主动重连；
- 每 20 分钟左右的浏览器 Cookie 刷新；
- 商品/订单/超时/买家互动轮询；
- 订单卡片触发的成交值和详情请求；
- 自动发货、擦亮、评价和求花动作。

聊天 WebSocket 本身仍需注册、心跳和发送消息，也可能被平台验证。本设计只能把非必要请求降为零或按需，不能承诺聊天一定不触发风控。

## 3. 目标组件

```text
SQLite system_settings
        │
        ▼
FeatureFlagRegistry ── 合法 key / default / dependencies / ui_targets
        │
        ├─ GET /feature-flags ────────────────┐
        ├─ PUT /feature-flags (事务 + revision)│
        │                                      ▼
        │                           FeatureFlagsContext
        │                              ├─ Settings 功能区
        │                              ├─ Sidebar 过滤
        │                              ├─ App mount/fallback
        │                              └─ 页面局部动作
        ▼
CookieManager.apply_feature_flags
        │ run_coroutine_threadsafe
        ▼
每个 XianyuLive.reconcile_feature_tasks
        ├─ start/cancel 可选 task
        └─ 事件/API require_feature 硬门禁
```

`app/feature_flags.py` 是定义中心，`system_settings` 是值中心。前端 registry 只镜像 UI 映射，不能声明后端运行默认。

### 4.3 configured 与 effective

```text
configured[auto_delivery_enabled] = true
configured[feature_items_enabled] = false
configured[feature_orders_enabled] = true

effective[auto_delivery_enabled]
  = auto_delivery_enabled
  AND feature_items_enabled
  AND feature_orders_enabled
  = false
```

API 同时返回两者。功能区显示用户保存值，并用“因商品模块关闭，当前不生效”解释 effective=false。关闭父级时不级联写子值。

依赖图必须无环，Registry 初始化时检测循环并让应用启动失败；不允许默默忽略错误依赖。

## 5. 持久化与 revision

### 5.1 复用 `system_settings`

不新增数据表。DB 初始化通过 `INSERT OR IGNORE` 增加缺失 key，读取时严格解析：

- 仅 `true/false`（大小写可规范化）或 SQLite 中等价 `1/0` 可迁移；
- API 请求只接受 JSON Boolean，不接受字符串 `"false"`；
- 数据库存量非法值采用 registry 安全默认，并记录不含秘密的 warning；API snapshot 返回 `warnings` 供管理员修复。

### 5.2 原子批量更新

`DBManager.update_feature_flags_atomic(flags, expected_revision)` 在 `self.lock` 和单一 SQLite transaction 中：

1. 验证完整 key 集合、类型和依赖定义；
2. 读取当前 snapshot/revision；
3. revision 不符则 rollback 并抛冲突；
4. 更新每个 key；
5. 更新 `feature_flags_revision` 单调整数；
6. 同事务 commit；
7. 回读 canonical snapshot。

任一写入失败时整批 rollback。通用 `PUT /system-settings/{key}` 遇到 feature key 返回 400/409 指引批量接口，防止绕过原子性。

## 6. 运行时门禁矩阵

| 开关 | task 创建/取消点 | 消息事件门禁 | API 门禁 | 保留路径 |
| --- | --- | --- | --- | --- |
| `scheduled_token_refresh_enabled` | `main/reconcile_feature_tasks` 的 `token_refresh_task` | 无 | 无 | `init` 按需刷新、人工恢复 |
| `browser_cookie_refresh_enabled` | `cookie_refresh_task` | 无 | 不门禁手动 QR/密码刷新 | 手动恢复 |
| `account_profile_auto_sync_enabled` | 连接后的 `_sync_account_profile` one-shot | 无 | 不门禁手动资料刷新 | `POST /cookies/{cid}/refresh-profile` |
| `item_sync_enabled` | `item_sync_task` | 无 | `/items/get-all-from-account` 等主动同步 | 本地已缓存消息商品信息 |
| `order_sync_enabled` | `order_sync_task` | 无 | `/api/orders/sync-sold`、refresh/import | 已有本地订单数据不删除 |
| `auto_polish_enabled` | `item_polish_task` | 无 | `/api/items/polish` | 无 |
| `delivery_timeout_alert_enabled` | `delivery_timeout_task` | 无 | 无/手工检查若存在 | 已有通知日志 |
| `feature_orders_enabled` | 上述订单子 task effective | `handle_message` 的订单 ID 预取、状态处理 | 订单 route group | 普通消息解析与显示 |
| `auto_delivery_enabled` | 无常驻 task | 付款提示、免拼卡片、`_handle_auto_delivery` | 手工发货/自动发货动作 | 普通聊天继续 |
| `feature_buyer_interaction_enabled` | `buyer_interaction_task` | 收货致谢、即时评价/求花 | rate/require-flower 等动作 | 三项账号配置 CRUD |
| `feature_auto_reply_enabled` | debounce task 不创建/取消 | `_schedule_debounced_reply` 前 | 关键词 mutation 可按产品决定门禁 | 手动消息发送、快捷短语 |
| AI/知识库/商品自动化/卡密模块 | 无或领域 task | AI 回复前 | 对应 mutation/action route group | 配置 GET 可保留用于恢复 |

门禁必须放在第一个副作用之前。例如 `feature_orders_enabled=false` 时，不能先调用 `fetch_order_real_values` 再决定不显示订单；`auto_delivery_enabled=false` 时，不能先拉订单详情再返回。

## 7. 任务收敛模型

### 7.1 生命周期

```text
PUT /feature-flags commit
        │
        ▼
CookieManager.apply_feature_flags(snapshot)
        │
        ├─ manager loop 可用 -> run_coroutine_threadsafe
        │       └─ 每个 instance.reconcile_feature_tasks
        │               ├─ false: cancel + await + ref=None
        │               └─ true: task 不存在/已完成才 create
        │
        └─ manager loop 不可用/超时 -> runtime_apply=pending
                └─ instance 周期轻量检查或下次重连重试收敛
```

保存 API 与账号运行在不同线程/事件循环。HTTP handler 不得直接 `task.cancel()` 或 `asyncio.create_task()` 操作账号 loop。`CookieManager` 是唯一跨线程桥。

### 7.2 即时与最终一致

数据库 commit 后 snapshot 是事实。任务应用不能与 SQLite 事务做真正的跨线程原子提交，因此 API 明确返回：

- `applied`：所有活跃实例已收敛；
- `pending`：配置已保存，某些实例等待下一次轻量检查/重连；
- `failed`：配置已保存但运行时应用发生可诊断错误，前端仍按已保存状态隐藏并提示查看日志。

运行时每个 loop 在执行外部调用前再次检查 effective，作为取消延迟的第二道防线。这样即使 task 正在 sleep 或取消尚未完成，也不会在关闭后发起下一次请求。

### 7.3 Token 特殊状态机

```text
连接开始
  ├─ current_token 缺失/过期 -> refresh_token -> /reg
  └─ current_token 可用       -> /reg

连接稳定
  ├─ scheduled=true  -> 到期刷新 -> 主动关闭 WS -> 重连
  └─ scheduled=false -> 不创建刷新 loop，不主动断线

连接失败/认证失败
  └─ 清理无效 token -> 重连 init 按需 refresh
```

关闭周期刷新不能通过把间隔改成 20 小时或无限大实现，因为那会混淆“关闭”和“延迟”，并留下 timer/task。必须以 task 不存在作为可验证状态。

## 8. API 合同

### 8.1 GET `/feature-flags`

所有已认证用户可读，返回非敏感可见性合同；这样普通用户也能按系统配置隐藏页面。修改仍只允许管理员。

```json
{
  "revision": 3,
  "configured": { "scheduled_token_refresh_enabled": false },
  "effective": { "scheduled_token_refresh_enabled": false },
  "definitions": [
    {
      "key": "scheduled_token_refresh_enabled",
      "group": "platform_background",
      "label": "周期 Token 刷新",
      "description": "关闭后仅在连接需要时刷新",
      "depends_on": [],
      "ui_targets": [],
      "risk_level": "high"
    }
  ],
  "warnings": []
}
```

不得返回环境变量、Cookie、Token、模板正文或其他 system setting。

### 8.2 PUT `/feature-flags`

仅管理员可调用。请求：

```json
{
  "expected_revision": 3,
  "flags": {
    "feature_items_enabled": false,
    "item_sync_enabled": false
  }
}
```

首版允许 partial patch 还是要求全量 map 必须二选一并由测试固定。推荐 partial patch + revision：服务端在事务内合并当前 configured，既避免前端发送未知新增键，也避免并发覆盖；“原子”指请求包含的所有键整体成功或整体失败。

成功返回完整 snapshot、`changed_keys` 和 `runtime_apply`。错误：

| HTTP | code | 场景 |
| ---: | --- | --- |
| 401/403 | 现有认证错误 | 未登录/非管理员 |
| 409 | `feature_revision_conflict` | expected revision 过期 |
| 422 | `invalid_feature_flag` | 未知 key、非 Boolean、空 patch |
| 500 | `feature_flags_update_failed` | 事务失败且已 rollback |

### 8.3 被关闭动作

```json
{
  "detail": {
    "code": "feature_disabled",
    "feature": "auto_delivery_enabled",
    "message": "功能已关闭，请到系统设置 > 功能区开启"
  }
}
```

使用 409 表示当前系统配置与动作冲突，不伪装 404，不泄露内部依赖图。

## 9. 前端状态与可见性

### 9.1 单一 snapshot

`FeatureFlagsProvider` 在认证成功后加载一次。App、Sidebar、Settings 和局部按钮都消费同一 Context。设置草稿与已保存 snapshot 分离：

- 编辑只改 local draft；
- 保存成功用 response 替换 snapshot；
- 保存失败保留 draft 供重试，但全局页面不隐藏；
- 409 时重新加载 snapshot，提示配置已被其他管理员修改。

### 9.2 页面回退

页面选择规则：

1. `active_page` 在 visible set 中：保留；
2. 不可见或未知：跳到 `messages`；
3. 若未来消息核心可配置且关闭：跳到 `dashboard`；
4. 覆盖 localStorage；
5. 禁用页面不 mount，而不是只加 `hidden`。

设置、账号、消息、总览、通知与日志、关于本轮始终可见，保证可恢复和可观察。

### 9.3 页面依赖

- `feature_items_enabled=false`：隐藏 ItemList；商品同步/擦亮/自动化即使 configured=true 也显示为“依赖未满足”。
- `feature_orders_enabled=false`：隐藏 OrderList；订单同步、超时、自动发货、买家互动 effective=false。
- `feature_cards_enabled=false` 不单独强制关闭自动发货 configured 值；若发货实现需要卡密，发货前仍由具体 delivery config 判定。自动发货的硬依赖只设 items + orders，避免文本/API 发货被卡密模块误伤。
- AI 与知识库独立：关闭知识库不禁止无知识库 AI；关闭 AI 不删除知识库管理数据。

## 10. 迁移与兼容

1. 现有四个 Boolean key 原值优先；不存在才插兼容默认。
2. 新 module/action key 默认模拟升级前行为，避免升级即停产；不会自动套用聊天模式。
3. 三项账号互动列逐行保持，不写 `UPDATE cookies`。
4. 历史环境变量只在缺键首启时作为可选默认；保存过数据库后永远数据库优先。若选择彻底弃用，需在 `.env.example` 和 Compose 注释中说明。
5. 推荐聊天模式由管理员通过功能区显式保存，形成审计 revision。
6. 回滚旧代码时新增 system setting key 被忽略，可留存；不执行 destructive migration。

## 11. 失败与恢复

| 故障 | 行为 | 恢复 |
| --- | --- | --- |
| DB Boolean 非法 | 使用安全/兼容默认并返回 warning，不执行高风险动作 | 管理员重新保存合法值 |
| 批量写中一项失败 | 整批 rollback，revision 不变 | 修复后重试 |
| revision 冲突 | 409，不覆盖他人配置 | 前端 reload 后重新编辑 |
| manager loop 不运行 | 保存成功、runtime pending | 启动/重连时按 DB 收敛 |
| 某实例取消超时 | 该实例 failed，其余继续；下一次副作用前仍查开关 | 查看日志、重连实例 |
| feature snapshot 加载失败 | 核心页保留、可选页 fail closed | 重试 GET，不用本地默认开启 |
| 当前页被关闭 | 立即回退 messages | 设置区重新开启 |
| Token 周期关闭后连接过期 | 重连 init 按需刷新；可能进入人工验证 | 使用既有人工恢复入口 |

### 12.2 旧维护者服务去耦

品牌扫描发现旧维护者身份还通过官网、邮箱、公告源、免费 AI 默认地址和商品详情默认地址参与运行。目标仓库没有提供这些服务的新地址，因此采用“精确旧默认迁移 + 自定义值保留”：

1. 代码和示例配置不再内置旧维护者域名；公告、AI、商品详情等地址为空时显示“未配置”并停止对应外部请求。
2. 数据库迁移只识别 P5.1 冻结的旧默认精确值；命中时清空/禁用并记录脱敏迁移事件，任何不同的用户自定义 URL 原样保留。
3. 新安装默认不连接任何维护者自建服务；管理员可自行填写兼容地址。
4. About 删除没有替代值的官网和邮箱，只保留目标 GitHub 仓库入口；不得把 GitHub noreply 地址冒充联系邮箱。
5. 公告 Worker 若继续保留，其页面标题、Worker 名和下载占位符使用新身份；客户端默认公告源仍为空，部署者显式配置后才启用。

### 12.3 上游来源与清理边界

根 README 的 fork 声明是唯一允许出现直接上游身份的第一方文本。旧上游徽章、作者宣传、二级来源链、fork 网络图表及其更新脚本/工作流全部移除。历史计划中的绝对旧目录改为 `<repo-root>`，旧容器/镜像标识改为当前机器 slug；只做机械身份规范化，不改历史测试结论。

以下内容不属于旧品牌残留：`LICENSE` 的许可证通用措辞、依赖锁文件中第三方包的作者/赞助/仓库元数据、Git 历史和 `.git` 内部对象。目标 GitHub 仓库已是正确的 `origin`，实现阶段不调用 GitHub API 改仓库设置，也不自动重命名本机工作区目录。

### 12.4 兼容与发布顺序

品牌任务必须在 Phase 1～4 全绿后执行。先迁移运行默认和源码身份，再更新分发标识并完成唯一一次生产构建，随后分别删除旧统计材料、机械规范化历史身份，最后重写 README；最终门禁只运行 detached build 和只读验证，并比较前后工作树证据，不再改内容。容器名变化可能让旧 Compose 实例残留，升级说明必须要求先备份并用当前 Compose 正常停机，再用新 Compose 启动；不得自动删除未知容器或 volume。

## 13. 被拒绝的方案

- **只把 3600 改成 72000**：仍有周期请求，不能表达真正关闭，也无法验证 task 不存在。
- **只隐藏 Sidebar**：后台 task、消息旁路和直接 API 仍运行，不满足风险降低。
- **继续逐键 `Promise.all` 保存**：中途失败会留下部分新状态，UI 和运行时无法判断真实结果。
- **关闭父模块时清空子配置**：违背未来重新开启和“是什么配置就是什么配置”。
- **把三项买家互动改回全局开关**：破坏账号隔离和既有测试。
- **所有功能都靠环境变量**：不能在前端保存，重启/Compose 与数据库会形成竞争事实源。
- **关闭所有 Token 获取**：WebSocket `/reg` 需要有效 Token，会直接破坏聊天。
- **为了即时生效重启整个账号/服务**：会中断聊天且可能制造额外重连；应只收敛可选 task。
- **只替换页面标题**：Docker、包名、About、工作流和构建产物仍会泄漏旧身份。
- **给旧维护者域名换一个猜测的新域名**：用户没有提供对应服务，可能造成隐私外发或功能误导；应为空/禁用并要求显式配置。
- **清空所有 URL 设置**：会误删用户自定义服务；只迁移精确旧默认值。
- **在多个文件保留上游介绍**：违背“只保留一条 fork 声明”，来源说明只属于根 README。
