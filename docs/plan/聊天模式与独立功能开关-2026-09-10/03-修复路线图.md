# 修复路线图

[返回 README](./README.md) · [上一篇：开发规范](./02-开发规范.md) · [下一篇：测试计划](./04-测试计划.md)

## 1. 总体路线

```text
Phase 1：数据与 API 合同
        │
        ▼
Phase 2：后台 task + 消息事件 + API 硬门禁
        │
        ▼
Phase 3：功能区 + Sidebar/App/局部动作同源隐藏
        │
        ▼
Phase 4：兼容迁移 + 索引/文档 + 全量与测试账号验收
        │
        ▼
Phase 5：品牌/外链/发布身份迁移 + 最终 README
```

五个阶段必须串行。前端不能先于后端 snapshot 合同实现，否则会形成临时默认；运行时不能先于原子持久化实现，否则任务状态无法判断；正式迁移和真实账号验收只能在全量自动门禁后进行；品牌与 README 必须等最终功能形态通过验收后再改，避免文档和界面二次漂移。

## 2. 里程碑

| 里程碑 | 对应任务 | 可交付结果 | 进入条件 | 退出条件 |
| --- | --- | --- | --- | --- |
| M1 开关合同冻结 | P1.1～P1.5 | registry、原子 DB、管理员 API、语义测试 | 工作区/调用图完成只读记录 | DB/API 专测和 core 通过 |
| M2 运行时真正关闭 | P2.1～P2.6 | task 收敛、消息/API 门禁、按需 Token | M1 完成 | 关闭路径平台 mock 调用为 0，聊天回归通过 |
| M3 前端同源隐藏 | P3.1～P3.6 | 功能区、保存、菜单/page/action 隐藏 | M2 完成 | 构建和本地浏览器验收通过 |
| M4 功能实现冻结 | P4.1～P4.4 | 兼容迁移、接口目录、完整验证、测试账号证据 | M3 完成 | 功能行为冻结，可进入品牌迁移 |
| M5 闲鱼卖家发布身份 | P5.1～P5.9 | 界面、外链、镜像、作者、README 和零残留证据 | M4 完成 | 品牌/构建/文档/全量测试全部通过 |

## 4. Phase 1 路线：先有可证明的配置合同

### 4.1 顺序

1. P1.1 只读列出当前所有 task、事件、API、页面和用户改动。
2. P1.2 写 registry/保留语义红灯。
3. P1.3 实现注册表与单事务 DB。
4. P1.4 新建 `/feature-flags` 管理接口并阻止逐键绕过。
5. P1.5 定向与 core 绿灯。

### 4.2 关键决策

- 使用 partial patch + `expected_revision`，事务内合并并返回完整 snapshot；
- 已有 key 不重命名，不创建 `feature_item_sync_enabled` 等重复项；
- 新 key 缺失时兼容旧行为，推荐聊天值不写入迁移；
- 买家互动三列不进入批量 payload。

### 4.3 回滚点

在 M1 后可安全回滚 API/registry 代码。新增 `system_settings` key 可留存，旧版本会忽略；不需要删除数据库数据。

## 5. Phase 2 路线：先停请求，再谈隐藏

### 5.1 顺序

1. P2.1 枚举全部旁路，特别是 `handle_message` 中订单详情预取和免拼分支。
2. P2.2 把可选 task 统一纳入 reconcile，并保留核心 task。
3. P2.3 用 CookieManager 在正确事件循环应用 snapshot。
4. P2.4 在消息事件最早副作用前门禁。
5. P2.5 在业务 API 最早副作用前门禁。
6. P2.6 验证周期 Token、人工滑块、重连和聊天。

### 5.2 上线阻断条件

出现任一情况不得进入前端阶段：

- 关闭开关后 mock 平台方法仍被调用；
- 重连后已关闭 task 再次创建；
- 取消可选 task 同时取消 heartbeat/消息监听；
- 关闭周期刷新后首次连接无法取得 Token；
- 买家互动总开关写坏账号级三列；
- API 只在 UI 隐藏，直接调用仍执行。

### 5.3 回滚点

保留 registry/DB/API，回滚运行时接线即可恢复旧任务行为。若 task reconcile 存在严重问题，可暂时把兼容默认保持开启并停止发布，但不得删除用户已保存值。

## 6. Phase 3 路线：已保存状态驱动 UI

### 6.1 顺序

1. P3.1 枚举全部菜单、section 和局部按钮。
2. P3.2 建立类型、API client、Context 和 UI registry。
3. P3.3 实现功能区草稿/原子保存。
4. P3.4 实现 Sidebar 过滤、页面不 mount 和 localStorage fallback。
5. P3.5 门禁局部动作并统一关闭提示。
6. P3.6 完成本地浏览器验收和阶段门禁。

### 6.2 UX 验收重点

- 设置页永远不能被自己隐藏；
- 关闭当前页面后跳到消息中心，不出现空白；
- 保存失败不隐藏任何东西；
- 刷新后保持服务端状态，而不是恢复旧前端缓存；
- configured=true、effective=false 有依赖说明；
- 重新打开模块后原 interval、模板和账号配置仍在。

### 6.3 回滚点

前端可单独回滚到静态菜单，后端门禁仍保护已关闭动作。若 Context 加载失败，核心页面 fail-safe 显示，可选页面 fail-closed 隐藏。

## 7. Phase 4 路线：兼容升级与发布

### 7.1 预发布

1. 备份 `data/`，记录文件 hash，不读取/输出秘密。
2. 在运行库副本演练升级、二次启动和代码回滚。
3. 验证已有 system Boolean 和每账号三项互动值逐值相等。
4. 完整运行 `--suite all --coverage --quality --database snapshot`。
5. 正式重建 API index/全量目录，连续两次输出一致。

### 7.2 目标部署切换

实现部署后不由迁移代码自动关闭业务。管理员进入“系统设置 > 功能区”，逐项保存 README 推荐聊天值。保存响应必须显示新 revision；运行日志确认对应 task 已取消。

### 7.3 最小真实验收

使用专用测试账号：

- 收一条普通消息、手动回一条；
- 在不执行真实交易动作的前提下回放/接收订单卡片，确认没有成交详情和发货调用；
- 稳定观察至少一个当前 Token 周期，确认 scheduled refresh 未运行；
- 检查人工验证入口仍可用于真实过期/挑战恢复；
- 核对三个账号级互动值未改变。

真实账号测试若触发风控，立即停止额外请求，保存脱敏日志，走现有人工验证；不得通过提高重试频率“验证修复”。

## 8. Phase 5 路线：最后统一品牌与发布身份

### 8.1 顺序

1. P5.1 只读冻结 tracked 文件中的旧名称、作者、仓库、域名、包、镜像、容器、静态产物和图片清单，并建立唯一允许的 fork 声明规则。
2. P5.2 先写品牌身份与旧服务精确默认迁移红灯。
3. P5.3 移除公告、AI 和商品详情的隐式旧维护者服务绑定，自定义值保留。
4. P5.4 修改登录页、Sidebar、移动端页头、About、HTML title、公告管理页和测试入口，统一显示“闲鱼卖家”。
5. P5.5 修改 npm、app-shell、Docker、Compose、GHCR、OCI label、Actions、Worker/User-Agent 等发布机器标识并重建前端。
6. P5.6 删除旧 fork 统计资产/脚本/工作流，并把来源链迁移说明改为中性功能迁移文档。
7. P5.7 独立机械规范化历史第一方文档中的旧名称、路径、作者、仓库、域名和容器/镜像标识。
8. P5.8 在实现已冻结后从头重写根 README，唯一保留一条直接上游 fork 声明。
9. P5.9 执行品牌静态合同、全量测试、浏览器验收和零残留扫描，比较门禁前后工作树证据且不再做内容修改。

### 8.2 品牌验收重点

- 登录页、桌面与移动导航、About、浏览器标签和公告管理页只显示“闲鱼卖家”；
- 目标仓库、release、issue、clone、GHCR、Docker label 和 npm 根包身份一致；
- About 只保留目标 GitHub，不显示没有新值的官网/邮箱；
- 空公告/AI/商品详情地址不发请求，精确旧默认被安全迁移，自定义地址不变；
- 根 README 的直接上游身份只出现于唯一 fork 声明；
- 许可证正文、依赖作者元数据和 Git 历史不被机械替换；
- 旧机器 slug 的历史绝对路径改成 `<repo-root>`，本机工作区不自动移动。

### 8.3 回滚点

品牌 UI 和文档可回滚，不应改变业务数据。外部服务迁移前必须记录 key、是否命中旧默认和备份 hash；若误伤自定义值，从备份恢复该设置。容器迁移不删除旧 volume；若新镜像启动失败，停新容器后用旧 Compose/镜像和同一数据卷恢复。删除的 fork 统计文件可从 Git 恢复，但最终交付不得重新引用。

## 9. 发布与回滚

### 9.1 发布顺序

```text
备份数据
  -> 部署 backend registry/API/runtime gates
  -> 部署 frontend feature UI
  -> 健康检查与 GET snapshot
  -> 管理员保存推荐聊天值
  -> 检查 task 收敛
  -> 测试账号聊天验收
  -> 冻结功能行为
  -> 迁移品牌、外链和发布身份
  -> 重建前端并清理旧身份材料
  -> 最后重写 README
  -> 零残留与全量发布门禁
```

后端必须先于前端。旧前端遇到新后端仍可使用系统设置；新前端遇到旧后端会缺 `/feature-flags`，因此不允许逆序滚动部署。

### 9.2 回滚步骤

1. 停止真实账号主动测试。
2. 保留数据库备份和当前 feature snapshot/revision 的脱敏记录。
3. 回滚应用代码/镜像；新增 system keys 留存，不做 DELETE。
4. 如需恢复旧业务行为，先回到新版本功能区显式开启所需功能，再回滚；不得直接编辑 SQLite。
5. 验证聊天连接、旧系统设置和账号级互动值。

### 9.3 紧急停用

若新版本出现平台请求失控，可通过批量 API 将所有高风险开关设 false，保留聊天核心。API 不可用时停止账号监听进程优先于手工改库；恢复前先定位门禁遗漏。

## 10. 风险登记

| 风险 | 概率/影响 | 预防 | 检测 | 处置 |
| --- | --- | --- | --- | --- |
| 消息旁路仍查订单 | 高/高 | 最早门禁 + mock call=0 | TC-RT-05～07 | 阻断发布 |
| 关闭后 task 睡眠未及时取消 | 中/高 | 即时 cancel + 调用前二次门禁 | task 状态与调用计数 | 标 pending，下一轮收敛 |
| HTTP 跨 loop 操作死锁 | 中/高 | CookieManager bridge + timeout | TC-RT-12～13 | 保存成功但运行 pending，禁止假 applied |
| 旧默认导致升级行为突变 | 中/高 | `INSERT OR IGNORE` + 副本矩阵 | TC-DB-07～09 | 回滚代码，保留 key |
| UI 保存部分成功 | 当前高/高 | 单 PUT + DB transaction + revision | TC-API-04～08 | 回读 snapshot，不信本地草稿 |
| localStorage 打开隐藏页 | 高/中 | visible set + 不 mount + fallback | TC-UI-09～12 | 清理并覆盖 active_page |
| 买家互动子配置丢失 | 低/高 | 禁止写 cookies 列 | 迁移前后逐值比较 | 从备份恢复，阻断发布 |
| Token 完全停刷导致聊天断开 | 中/高 | 按需刷新保留 | TC-TOKEN-02～05 | 恢复连接，不打开周期任务 |
| 用户误认为零风控 | 中/高 | UI/README 明确边界 | 文案测试/验收 | 更正说明，不追加危险自动化 |
| 覆盖用户未提交改动 | 中/高 | 每 Phase git diff 审计 | status/hunk 记录 | 停止并请求人工合并 |
| 旧品牌遗漏在移动端/静态 bundle | 高/中 | 源码矩阵 + 生产重建 + tracked scan | TC-BRAND-01～04、10 | 阻断发布并回到对应表面修复 |
| 旧服务默认继续外发 | 中/高 | 空默认 + 精确迁移 + 请求 spy | TC-BRAND-05～07 | 禁用该服务并恢复自定义值 |
| 模糊迁移误清用户 URL | 低/高 | 仅精确值匹配 | TC-BRAND-08 | 从备份恢复，阻断发布 |
| 新容器名留下旧实例 | 中/中 | 升级说明要求正常停旧再启新 | TC-META-04 | 停新实例，保留 volume 后恢复 |
| 上游身份重复或许可证误改 | 中/高 | 唯一 fork 行断言 + LICENSE hash | TC-README-02、TC-BRAND-11 | 恢复许可证，删除重复归属 |

## 11. 完成判定

路线图完成不等于功能“看起来可用”。只有 00 执行文档全部勾选、04 的出口条件满足、05 的关键 P0/P1 用例通过、品牌零残留与唯一 fork 声明成立、根 README 已按最终代码重写且工作区保护证据完整，才可宣布交付。
