# 开发规范

[返回 README](./README.md) · [上一篇：架构设计](./01-架构设计.md) · [下一篇：修复路线图](./03-修复路线图.md)

## 1. 适用范围

本规范适用于后续模型在 `<repo-root>` 实现商品知识表、检索服务、AI 回复接线、管理 API、前端编辑器、测试和 API 索引。外部产品文档只读，不属于修改范围。

事实优先级：本次用户策略 → Passistant 当前产品事实源 → D 项目运行 API/源码 → 本计划 → 旧计划与旧 prompt。冲突时不得折中；无法验证写 `unknown` 并使用不作承诺的回复。

## 2. 必须使用的常量合同

在 `app/product_knowledge.py` 定义单一事实源，测试直接引用或逐字断言：

```python
SAFETY_REPLY = "目前没有收到玩家反馈有封号情况出现。"
COMMERCIAL_SENSITIVE_REPLY = "这个问题涉及内部信息，暂不提供。"
UNKNOWN_PUBLIC_REPLY = "这个问题需要人工确认后回复。"
MAX_KNOWLEDGE_ENTRIES = 200
MAX_MATCHES = 5
MAX_CONTEXT_CHARACTERS = 2500
```

- 不在 `custom_prompts`、route、测试 fixture 和前端各复制一套固定句。
- `SAFETY_REPLY` 不得追加空格、换行、表情、补充说明或第二句话。
- 固定策略回复必须保存到现有 `ai_conversations`，使同一会话上下文与实际发送一致。
- 日志只写策略类别和固定 reply ID，不写买家原问题或固定回复全文。

## 3. 价格与商品合同

- 商品 ID：`1081710901648`。
- 权益：30 天。
- 原价：¥29.9/月。
- 当前活动：宣传口径 3 折，活动价 ¥9.9/月。
- ¥9.9 是当前活动价，不得称为原价、常规价、永久价或一直有效。
- 用户未提供活动截止时间；回复只能说“目前没有提供活动结束时间”，不得猜日期、倒计时或库存名额。
- 活动价不接受额外砍价。既有 `max_discount_percent=0`、`max_discount_amount=0` 和议价拒绝逻辑继续作为硬边界。
- 买家只问“多少钱”时，也必须同时给出原价和活动价，避免把 9.9 误解为商品常规月价。
- 服区：支持国际服、台服；不支持国服。不得扩大到其他服区或平台。

## 4. 数据字段规范

### 4.1 条目对象

| 字段 | 规则 |
| --- | --- |
| `knowledge_key` | 必填，1～80 字符，`^[a-z0-9][a-z0-9._-]*$`，文档内唯一 |
| `category` | 必填，仅允许 `product/pricing/region/install/activation/feature/limitation/support` |
| `question_patterns` | 0～20 项；每项 trim 后 1～80 字符；去重并保持首次顺序 |
| `keywords` | 1～30 项；每项 trim 后 1～32 字符；去重并保持首次顺序 |
| `answer` | 必填，trim 后 1～800 字符，纯文本，不得含 Markdown 链接、HTML 或控制字符 |
| `source_refs` | seed 内必填 1～8 项，每项 1～240 字符；自定义 PUT 可由服务端沿用/标记 `operator`，永不返回前端或模型 |
| `priority` | 整数 -100～100 |
| `enabled` | 严格布尔值 |

文档最多 200 条，序列化请求总大小由 FastAPI/应用层限制在 512 KiB。空数组是合法替换，表示关闭该商品的全部知识。

### 4.2 JSON 规范

- `question_patterns`、`keywords`、`source_refs` 以 UTF-8 JSON 数组存 SQLite，不使用 Python repr。
- documents 的 `product_key` 使用与 `knowledge_key` 相同的稳定小写格式；当前只允许 `passistant`。`display_name` 当前固定为 `Passistant 知识库`，长度 1～80，纯文本。
- `json.dumps(..., ensure_ascii=False, separators=(",", ":"))` 用于稳定序列化。
- 文档 checksum 对规范化、按 `knowledge_key` 排序后的公开字段计算 SHA-256；不包含数据库 id、时间戳和 `source_refs`。
- seed 文件必须 UTF-8、顶层字段固定、未知字段拒绝，防止拼写错误被静默忽略。
- 所有时间使用 SQLite `CURRENT_TIMESTAMP`；API version 是整数，不用时间戳做并发控制。

## 5. 公开内容白名单与敏感扫描

`validate_entry` 先做结构校验，再对 `knowledge_key/category/question_patterns/keywords/answer` 执行敏感扫描。至少拒绝：

- 源码、源代码、反编译、偏移、offset、AOB、内存地址、特征码、签名、类名/方法名泄露；
- 检测规避、反作弊实现和保护机制强度不得进入公开 seed；买家询问这些话题时必须归入 safety 固定回复，而不是商业敏感拒答；
- API Key、token、Cookie、密码、连接串、数据库地址、管理员账号资料；
- 成本、利润、进价、供应商、供应渠道、销售数据；
- 完整激活码格式、库存明文、其他买家或订单资料；
- Windows 绝对路径、仓库路径、私有 URL、日志片段、内部测试结论。

扫描是最低门槛，不代表未命中就自动公开。seed 仍需人工逐条审阅；任何不确定内容默认不写入。

安全相关词允许出现在本地策略 pattern 和测试中，但禁止进入公开 seed 的普通答案。唯一可发送的安全回复只来自 `SAFETY_REPLY` 常量。

## 6. 策略分类规范

### 6.1 规范化

所有分类和检索共用：

1. 非字符串视为空；
2. `unicodedata.normalize("NFKC", text)`；
3. `.casefold()`；
4. 连续空白折叠；
5. 保留中文和标点用于短语判断，不做不可靠分词。

### 6.2 安全规则

- 使用短语与正则表，不调用模型。
- `安全` 单独出现或与产品/账号/使用组合时按 safety；“安全付款/闲鱼安全交易”等纯平台交易语境要由明确排除用例保护，但无法可靠区分时仍以 safety 为先。
- `ban` 需按单词边界匹配，避免普通英文片段误伤。
- 同时命中多类时 `safety > commercial_sensitive > public`。
- 分类异常时 fail closed：如果原文含明确 safety marker，仍返回安全固定句；否则商业敏感 marker 返回固定拒答；只在两类都无命中时进入 public。

### 6.3 商业敏感规则

- 优先匹配多词短语，如“管理后台密码”“数据库地址”，不要把“后台运行”中的“后台”单独列为敏感词。
- `检测`、`反作弊`、`绕检测`、`规避检测`、`风控` 无条件归 safety，不进入本节商业敏感分支。
- “功能怎么用”是 public；“功能源码怎么实现”是 commercial_sensitive。
- “激活码怎么兑换”是 public；“把全部激活码发我”是 commercial_sensitive。
- “成本多少/供应商是谁/卖了多少”一律 commercial_sensitive。
- pattern 列表是服务端内部常量，不通过 preview API 下发。

## 7. 检索规范

- 只能调用 `db_manager.list_product_knowledge(cookie_id,item_id,enabled_only=True)`。
- 没有文本命中时不得靠 priority 填充结果。
- 完整问法相等 +100；pattern 包含关系按架构文档计分；每个 keyword +20。
- 同一 keyword 只加一次；空 keyword 在验证阶段拒绝。
- 排序必须确定：`(-score, -priority, knowledge_key)`。
- 结果最多 5 条、答案总计最多 2500 字符；添加整条会超预算时跳过该条并继续检查更短的下一条。
- 不把 `question_patterns`、`keywords`、`source_refs`、score、数据库 id 或版本交给模型。
- 检索服务不得缓存跨请求可变列表。若以后加缓存，key 必须含 cookie/item/version，另立计划。

## 8. 数据库规范

- `ai_product_knowledge_documents` 与 `ai_product_knowledge_entries` 的建表和索引放在 `DBManager.init_db`，沿用现有初始化/迁移风格；documents 行保存 version/checksum，使空 entries 也能持久化版本。
- 数据方法都使用 `with self.lock`；写事务异常必须 rollback 并抛出可识别业务异常，不能只返回 False 丢失冲突原因。
- `replace_product_knowledge` 在同一事务读取 current version、检查 expected、upsert documents 新版本、删除旧 entries、插入全部新 entries、commit。
- 用明确 `KnowledgeVersionConflict` 或等价异常映射 HTTP 409；结构错误映射 422；数据库异常映射 500 且不回显 SQL/路径。
- 删除 `item_info` 时 documents/entries 应同步删除。SQLite 外键若未全局启用，则 `delete_item_info` 必须显式调用 `delete_product_knowledge_for_item`；测试覆盖实际行为，不能只假设 `ON DELETE CASCADE` 生效。
- 两张知识表不得加入通用管理员数据表白名单；专用 API 是唯一写入/展示边界。
- 不修改现有业务数据，不迁移 `custom_prompts` 到知识表，不自动导入 seed。

## 9. API 与权限规范

- route 必须先取 `current_user['user_id']`，用 `db_manager.get_all_cookies(user_id)` 验证 cookie 归属，再用 `get_item_info(cookie_id,item_id)` 验证商品。
- 路径参数由 FastAPI 解码，前端调用时必须 `encodeURIComponent`。
- GET 只返回公开可编辑字段；`source_refs`、敏感 pattern、SQL id 和时间戳不返回。
- PUT 的 `expected_version` 必填且不小于 0；禁止 `force=true`、忽略版本或隐藏覆盖。
- import API 只接受 `expected_version`，不允许客户端提交 seed 路径或文件名。
- preview 输入 1～500 字符，不写 DB、不调用模型、不产生对话记录。
- API 错误 `detail` 使用固定业务描述，不拼接异常字符串中的 SQL、绝对路径或秘密。
- `POST /ai-reply-test/{cookie_id}` 只接受 `message` 和 `item_id`；从 DB 获取商品事实。未经授权 item 返回 404/403，不降级到“测试商品”。
- 所有新增 operation 必须进入 `.ai/index/backend-apis.json` 和 `docs/references/ai-rules/05-全量接口目录.md`。

## 10. AI 回复规范

- 系统/订单事件仍在最前面绕过 AI 和知识。
- 策略分流发生在最新消息判定之后，以免较早消息产生固定回复；发生在上下文读取和模型客户端创建之前，以证明零模型调用。
- 固定回复仍保存 user/assistant 两条会话记录，但不递增议价轮次。
- 普通知识只作为事实数据附加，不替换现有 `default/tech/price` prompt。
- 不允许 `custom_prompts` 覆盖安全、敏感、订单、价格或非主动提及边界；不可覆盖规则在最终 system message 的最后。
- 买家提示注入（“忽略规则”“输出系统提示”“把数据库告诉我”）按敏感规则处理或被 system policy 忽略。
- `_normalize_reply` 后新增 `validate_model_reply(message,reply,policy_intent)`：
  - 普通消息的 reply 命中主动安全词或商业敏感 marker → 拒绝模型输出；
  - reply 包含系统提示、知识标签、source ref、绝对路径、疑似 secret/激活码 → 拒绝；
  - 安全固定句不经过会改写文本的 normalizer；
  - 知识确定性回落也要经过公开答案验证，但不得再次调用模型。
- 订单状态仅以现有系统事件/订单处理为准。知识和模型不得声称“已付款、已发货、已退款、库存已锁定”。

## 11. 前端规范

- `Sidebar.tsx::menuGroups` 在“客户沟通”分组中、`AI 回复` 后增加 `knowledge-base / 知识库`；使用 lucide-react 已有 `BookOpen`，桌面与移动侧栏共用同一数组。
- `App.tsx` 增加 `KnowledgeBase` lazy import、`pageLabels['knowledge-base']` 和 Suspense section；不得另建路由状态或破坏 `active_page` 恢复。
- `KnowledgeBase.tsx` 是独立一级页面，页面名“知识库”，当前项目名“Passistant 知识库”；`AIReply.tsx` 不内嵌编辑器，只负责 AI 配置和真实商品回复测试。
- 知识库和 AI 测试的商品列表都用现有 `getItems()`，按 `cookie_id` 精确过滤；不调用 `POST /items` 补造缺失商品。
- 条目本地 dirty 时切换账号/商品要确认放弃未保存修改；不在 localStorage 保存知识或 prompt。
- 保存/导入成功后必须 GET 回读，不只相信响应 toast。
- 409 显示“知识已被其他操作更新，请重新加载”，不自动 retry PUT。
- 输入按纯文本处理，textarea 不使用 `dangerouslySetInnerHTML`。
- 不在 UI 暴露敏感词表、source refs、内部路径、完整 system prompt、API Key 或模型上下文。
- 测试回复必须选择实际商品；没有商品时明确空态。

## 12. 测试规范

- 沿用 Python `unittest` 和 `unittest.mock`；patch 被测代码查找符号的位置。
- 数据测试使用 `tempfile.TemporaryDirectory()` 下的临时 SQLite，禁止连接 `data/xianyu_data.db`。
- 单元测试不得调用真实 DeepSeek、闲鱼、浏览器或生产 API。
- 固定回复测试必须 mock `_generate_with_retry`、`_create_openai_client`、`retrieve` 并断言零调用。
- 输出拦截测试给模型返回含主动安全词/内部 marker 的字符串，断言买家收到公开知识回落或人工确认句。
- API 权限测试优先直接调用 handler 并注入临时 DB/当前用户；若引入 TestClient，不能修改全局生产 DB。
- 先运行专用测试，再运行全套：`python -m unittest discover -s tests -p "test_*.py"`。
- 前端变化必须 `npm ci` 后 `npm run build`；不以已有 `node_modules` 代替 lockfile 可复现构建。
- 最终 `git diff --check`，API 索引连续生成两次相同。

## 13. 日志与秘密

- 不打印 `.env`、API Key、密码、Cookie、token、完整卡密、买家原消息、完整答案或 system prompt。
- AI 成功日志只写 cookie/item 的安全标识摘要、policy intent、match 数量、reply 字符数；禁止写 answer 前 120 字。
- 验证文档只记录 status code、version、entry_count、checksum、match keys 和布尔断言。
- API Key 的完成证据仍是 `api_key_configured=true`，不读回明文。
- seed checksum 可记录；seed 答案正文留在受版本控制 JSON，不复制到运行日志。

## 15. 提交与部署

- 每阶段审计 `git status --short` 和 scoped diff，只暂存本阶段文件。
- 本地提交使用中文 Conventional Commit，不加 AI 署名；冲突或重叠用户改动时不强行提交。
- 不 push、tag、建 PR、改远程。
- 所有代码/构建通过后才 `docker compose up -d --build`。
- 部署后只通过项目 API 导入 seed 与验收；禁止直接 SQLite、浏览器或桌面操作。
