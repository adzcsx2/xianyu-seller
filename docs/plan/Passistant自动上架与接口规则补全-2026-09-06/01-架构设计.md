# 架构设计

[返回 README](./README.md) · [上一篇：执行文档](./00-执行文档.md) · [下一篇：开发规范](./02-开发规范.md)

## 1. 设计目标

本任务不是“自动发布商品”，而是把一个已由用户发布的商品接入现有自动化能力：

1. 通过认证 API 唯一确定商品 `1081710901648` 的所属账号。
2. 把已经生成并验证的 100 个 Passistant 月卡导入一个卡密库存。
3. 用一个普通单规格配置实现每单自动发 1 码。
4. 从根 `.env` 读取 DeepSeek 凭据/模型/地址，保存商品知识与安全边界并隔离测试。
5. 让运行时 OpenAPI、静态索引和 AI 全接口目录保持一致。
6. 全程不使用浏览器、桌面自动化或直接数据库写入。

## 2. 当前能力审计

### 2.1 商品管理前端

`frontend/components/ItemList.tsx` 与 `frontend/services/api.ts` 已提供：

- 从指定闲鱼账号同步已有商品；
- 手动添加本地商品记录；
- 查看/编辑本地商品详情；
- 删除本地商品记录和批量删除；
- 一键擦亮已有商品；
- 普通/多规格与多数量发货能力开关；
- 逐商品专属发货配置；
- 通用发货规则；
- 发货保护规则与个人黑名单；
- 卡密库存选择和配置完整度展示。

`frontend/components/ProductAutomation.tsx` 提供素材记录编辑/删除、筛选规则、删除规则预览、任务运行记录和修复入口。`publish_status`、`published_item_id` 和 `publish_trace_code` 是本地素材字段，不构成外部发布调用。

### 2.2 已有 API 能力

| 能力 | API | 副作用 |
|---|---|---|
| 管理员登录 | `POST /login` | 创建内存会话 token |
| 会话校验 | `GET /verify` | 无业务写入 |
| 账号读取 | `GET /cookies/details` | 无 |
| 商品读取 | `GET /items` | 无 |
| 同步已有商品 | `POST /items/get-all-from-account` | 读取闲鱼已有商品并更新本地缓存 |
| 本地手动记录 | `POST /items` | 只写本地记录，不发布 |
| 卡密读取/创建 | `GET/POST /cards`、`GET /cards/{id}` | 创建时写当前用户 card |
| 专属发货配置 | `GET/PUT /items/{cookie_id}/{item_id}/delivery-config` | 保存当前用户商品绑定 |
| AI 设置 | `GET/PUT /ai-reply-settings/{cookie_id}` | 保存账号设置 |
| AI 隔离测试 | `POST /ai-reply-test/{cookie_id}` | 调用配置模型，不进入买家会话 |

没有经源码验证的“创建新的外部闲鱼商品” API。这个能力是真实缺失，不是 API 索引遗漏。

### 2.3 DeepSeek .env 与运行配置

根 `.env` 目前存在非空 `API_KEY`、`MODEL_NAME`、`MODEL_BASE_URL`，且模型名已核验为用户指定的 v4flash。静态搜索没有发现这三个通用变量被应用源码或 compose 自动映射到账号 AI 设置；compose 使用的是另一组 `DEFAULT_AI_*` 变量，而账号设置存储在数据库。

因此目标架构不是修改 `.env`，而是让执行进程安全读取这三个值，然后通过 `PUT /ai-reply-settings/{cookie_id}` 写入唯一账号。实际启用以账号 `ai_enabled=true`、`api_key_configured=true` 和 test API 成功为证据。

### 2.4 API 发现链缺陷

当前静态索引生成器已知问题：

- 把注释 `# @app.post('/api/orders/verify-all')` 当成 route；
- 未解析 `APIRouter(prefix=...)`，使七条验证码 route 丢失 `/api/captcha` 前缀；
- 主应用的 `POST /api/captcha/manual-session` 本身正确，验证码运行时共八条 operation；
- catch-all `/{path:path}` 与 OpenAPI `/{path}` 需要仅对该 handler 做规范化；
- 缺少可靠 handler、schema 与 auth/owner 元数据。

旧的 221/220 差异来自扫描器缺陷，不能推断存在未发现的发布接口。

## 3. 目标数据流

```text
安全会话密码
  → POST /login → Bearer token（仅内存）
  → GET /cookies/details + GET /items
  → 必要时 POST /items/get-all-from-account
  → 唯一 cookie_id ↔ item 1081710901648
        ↓
Passistant 既有批次（只查）
  → QueryBatch/ListCodes/ValidateExport
  → TXT/CSV/DB hash 集合一致
  → GET /cards → 复用或 POST /cards 一次
  → GET/PUT/GET delivery-config
        ↓
根 .env（只读）
  → API_KEY + MODEL_NAME + MODEL_BASE_URL（仅进程内）
  → GET/PUT/GET ai-reply-settings
  → POST ai-reply-test × 5
        ↓
OpenAPI + 源码 → 修复索引 → 05-全量接口目录.md
  → 三套 METHOD PATH 集合一致
```

所有箭头串行。若读取已证明目标状态存在，业务写入应跳过。

## 4. 身份、归属与幂等边界

- 登录身份固定为 `admin`，实际 user/admin 状态由 API 回读。
- `cookie_id` 必须来自当前用户账号集合，不能猜测。
- 目标 item 必须通过同步或现有 GET 与唯一 `cookie_id` 关联。
- card 复用要求完整批次号、类型、启用、单规格和 100 行集合全部一致。
- delivery config 与 AI settings 都使用同一个唯一 `cookie_id`。
- AI GET 不返回 Key 明文；覆盖 Key 仅使用本次用户授权的根 `.env`。
- 任一歧义进入 `blocked`，不能默认取列表第一项。

## 5. 激活码架构

事实源分两层：

- Supabase：批次与 code 表保存批次、SHA-256、五字符 suffix 和状态，不保存明文。
- 本地导出：初次生成的 TXT/CSV 是唯一完整明文库存。

批次 `XYB-PASSISTANT-30D-20260906-1081710901648` 已生成，不允许重建。D card 只是核验后的发货副本。

一致性要求：batch/metadata/TXT/CSV/D card 都为 100，duration 30、channel xianyu，TXT/CSV/card 集合相同，hash/suffix 对应。导出丢失时不能从数据库恢复，必须停止并走精确禁用流程，绝不能补生成。

## 6. 自动发货配置

```json
{
  "enabled": true,
  "is_multi_spec": false,
  "variants": [
    {
      "display_name": "Passistant 30天月卡",
      "spec_text": "30天",
      "spec_payload": null,
      "platform_sku_id": "",
      "card_id": 123,
      "delivery_count": 1,
      "enabled": true,
      "binding_enabled": true,
      "source": "manual"
    }
  ]
}
```

`card_id` 必须替换为唯一真实 ID。完成证据是 GET 返回 `configured=true`、`complete=true`、一个 variant、`delivery_count=1`。

## 7. DeepSeek 回复架构

Key、模型和 base URL 来自根 `.env`。其余固定设置：

| 字段 | 值 |
|---|---|
| `ai_enabled` | `true` |
| `context_enabled` | `true` |
| `context_message_limit` | `12` |
| `context_expire_minutes` | `120` |
| `max_discount_percent` | `0` |
| `max_discount_amount` | `0` |
| `max_bargain_rounds` | `1` |
| `custom_prompts` | JSON 字符串：`default`、`price`、`tech` |

共同事实：

- Passistant 是 POE2 Windows x64 叠加层辅助软件；
- 30 天月卡 ¥9.9，固定价；
- 只支持国际服、台服，不支持国服；
- 确认付款后每单发送一个激活码；
- 官网 `passistant.vip`，管理员运行 `Launcher.exe`，注册/登录后在个人中心兑换；
- 不知道订单状态时要求订单信息或转人工；
- 不作官方授权、绝对安全或零封号承诺。

## 8. API 规则架构

最终文件 `docs/references/ai-rules/05-全量接口目录.md` 每个 runtime operation 一条记录，至少包括 method/path、handler/source、auth/owner、request/response schema、关键错误与副作用；无法验证写 `unknown`。

生成后比较 runtime OpenAPI、`backend-apis.json`、全量接口 MD 三个规范化集合，要求完全相等且无重复。

## 9. 失败与恢复

| 失败 | 行为 |
|---|---|
| 登录密码不可用/错误 | blocked，不尝试浏览器 token |
| 多账号或商品归属歧义 | blocked，不选第一项 |
| 同步后商品仍缺失 | blocked，不调用 `POST /items` 伪造 |
| 商品价格/状态异常 | blocked，由用户确认 |
| 导出缺失或集合不一致 | 停止 card/delivery；精确 DisableBatch preview，授权后执行；不再生成 |
| card 部分匹配 | blocked，不更新、不新建第二 card |
| delivery 不完整 | blocked，不用通用规则掩盖 |
| .env 必需键缺失 | blocked，不猜模型/Key/地址 |
| AI test 失败 | 保留安全错误类别，不自动换模型/地址 |
| 索引与 OpenAPI 不一致 | 修生成器/测试，不手工掩盖 |

## 10. 架构决策

- AD-01：以用户已发布 item 为唯一事实，不实现发布能力。
- AD-02：同步失败时阻断，不用 `POST /items` 制造看似成功的记录。
- AD-03：先验证既有批次，再复制到 D card；永不补生成。
- AD-04：根 `.env` 是 DeepSeek 执行输入，账号 API 回读是生效事实。
- AD-05：OpenAPI + 源码共同约束接口目录；静态索引只是发现工具。
- AD-06：所有生产状态串行写入并立即回读。
