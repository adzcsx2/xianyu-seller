# Testing Rules

## Authoritative entry point

- Use `python scripts/run_tests.py` as the project-wide automation entry point.
- Operational examples and troubleshooting are in `docs/guide/自动化测试指南.md`.
- The runner keeps the existing Python `unittest` style and classifies tests into
  `core`, `e2e`, and `all`; use `--list` to inspect the current membership.
- Install test tooling with `python -m pip install -r requirements-test.txt` and
  install the project browser with `python -m playwright install chromium`.
- Do not use Codex/Claude desktop control, native UI automation, or manual clicking
  as a required acceptance dependency. Browser behavior is exercised through
  Python Playwright in headless mode.

## TDD and test placement

- For behavior changes, add or update a failing test first, run it to establish a
  valid RED state, implement the smallest fix, and rerun the same target to GREEN.
- Keep the existing naming pattern `tests/test_*.py` and use `unittest.TestCase`
  or `unittest.IsolatedAsyncioTestCase` as appropriate.
- Patch a dependency where the code under test looks it up. Mock HTTP, browser,
  AI, mail, time, and platform calls at an explicit service/manager seam.
- Never move a Mock, Stub, Spy, fake response, or test-only import into `app/`,
  `utils/`, `Start.py`, `XianyuAutoAsync.py`, or frontend production source.
- Cover relevant invalid input, empty responses, timeout/error codes, auth failure,
  lifecycle cleanup, concurrency, rollback, and account isolation cases.

## Test layers

| Layer | Purpose | Project mechanism |
|---|---|---|
| Unit/core | Parsers, policies, state machines, service behavior, error paths | `unittest`, `unittest.mock`, targeted `test_*.py` modules |
| Database/API integration | SQLite schema/migrations, FastAPI validation, auth and route contracts | Real temporary SQLite or a consistent live-DB snapshot plus FastAPI `TestClient` |
| Headless E2E | Real built page, HTTP boundary, worker thread, and user-visible behavior | Python Playwright headless, random localhost port, semantic locators |
| Frontend/build | Type correctness and production bundling | Direct Node TypeScript check and detached `frontend/scripts/build-test.mjs` |
| Deployment config | Compose syntax and interpolation | `docker compose ... config --quiet` for all three Compose files |

- Existing static source/string assertions are supplementary regression checks;
  they do not replace a behavior-level API or headless browser assertion.
- E2E tests must bind a random free port, must not reuse the running port 8080,
  and must wait for an observable response/state instead of arbitrary sleeps when
  a deterministic event is available.
- Add a browser test module to `E2E_TEST_MODULES` in `scripts/run_tests.py`; all
  other `tests/test_*.py` modules belong to `core` automatically.

## Database policy

- This is a single-user installation, so direct real-database verification is
  permitted. Always report whether a run used `temp`, `snapshot`, or `live` mode.
- `snapshot` is the normal repeatable mode. It creates a transactionally consistent
  SQLite backup (including WAL state), runs against the disposable copy, and cleans
  it after the worker process exits.
- `temp` starts from a blank disposable database and is preferred for schema,
  migration, isolation, rollback, and destructive-path tests.
- `live` points tests at the real database. Because importing the application and
  many tests may write, it requires `--allow-live-writes`; the runner creates a
  timestamped SQLite backup under `backups/test-runs/` before execution.
- Read-only manual/API acceptance may query the live database directly. Never run
  destructive migration, delete, reset, rollback, or fault-injection scenarios on
  it outside the guarded runner.
- Do not connect tests to a running database accidentally by omitting `DB_PATH`.
  The runner sets it explicitly and also enables UTF-8 output and disables SQL log
  noise for the test worker.

## Commands and change-based gates

Run from the repository root:

```powershell
# Inspect suite membership without opening a database.
python scripts/run_tests.py --list

# Smallest relevant RED/GREEN target.
python -m unittest discover -s tests -p "test_<area>.py" -v

# Fast project regression without browser modules, using real-data shape safely.
python scripts/run_tests.py --suite core --database snapshot

# Browser behavior without desktop control or real Xianyu interaction.
python scripts/run_tests.py --suite e2e --database snapshot

# Complete local quality run: all Python tests, coverage, typecheck, detached
# frontend build, all Compose configs, and git diff whitespace validation.
python scripts/run_tests.py --quality --database snapshot

# Explicit real-database run. A backup is created before any test imports the app.
python scripts/run_tests.py --suite core --database live --allow-live-writes
```

| Changed area | Minimum verification |
|---|---|
| Documentation/rules only | `git diff --check` plus rule/link consistency review |
| Pure backend utility/service | Targeted RED/GREEN test, then `--suite core` |
| Database, migration, auth, or API | Targeted integration tests on `temp` and/or `snapshot`, then `--suite core` |
| Frontend source | Targeted contract/E2E test plus the frontend checks included by `--quality` |
| Browser/login/captcha | Relevant unit tests plus `--suite e2e` with installed Chromium |
| Docker/config/dependency/release candidate | `--quality --database snapshot` |

- The detached test build writes only below `logs/test-artifacts/`; it must not replace or
  delete the committed `static/` assets. Use the production `npm run build` only
  when the task explicitly requires regenerated production assets.
- CI/release workflow changes are outside this framework unless the user requests
  them separately.

## Coverage and evidence

- The current legacy production-code baseline is approximately 28%. The local
  full-quality gate starts at 20% to prevent regression without making the legacy
  repository untestable.
- New or materially changed testable production logic must target at least 80%
  line and branch coverage in the changed module, with critical auth, delivery,
  pricing, migration, and risk-control branches explicitly tested.
- Do not raise the global threshold above the measured baseline without adding the
  tests that make the new threshold pass. Ratchet it upward when coverage improves.
- Test logs, coverage data/XML, and detached frontend output are written under
  `logs/test-artifacts/<run-id>/`. These artifacts are ignored and may contain
  diagnostics; do not copy secrets, cookies, tokens, buyer messages, or card data
  into reports.
- Report PASS, FAIL, or NOT VERIFIED for every applicable gate. Desktop-control
  failure only makes a manual visual check NOT VERIFIED; it is not a reason to skip
  the headless E2E suite.
- A skipped browser test is not a pass. Record the missing prerequisite and the
  exact install command, or run the non-browser suite and label browser coverage
  NOT VERIFIED.
