# Architecture Boundaries

- Keep FastAPI route registration and request/response validation at the API boundary. Keep reusable business behavior in the existing `app/`, `app/services/`, and `utils/` modules.
- Reuse `db_manager`, `Config`, existing managers, helpers, and frontend request utilities before adding a new abstraction.
- New business logic must not import tests or mock data. External HTTP, SQLite, browser, file, and mail access belongs behind an existing manager/service boundary or an explicit constructor/function dependency.
- Do not instantiate a repository or external client, or issue a real network call, inside a pure business function. Preserve existing module-level patterns when a task does not include an architecture refactor.
- Keep authentication and authorization checks at the route/dependency boundary. Verify caller scope before reusing an existing endpoint.
- Keep `frontend/services/api.ts` and `frontend/lib/request.ts` as the normal frontend-to-backend boundary. Do not scatter raw business `fetch` calls through components unless the local area already requires it.
- Production paths are `app/`, `utils/`, `Start.py`, and frontend source. They must not contain Mock/Stub/Spy fixtures or test-only imports; test-only doubles belong under `tests/`.
- There is no verified repository Linter enforcing these boundaries. Do not add one as part of a routine task; if a boundary configuration change is requested, plan it first.
