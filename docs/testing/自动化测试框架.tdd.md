# Local Automation Test Framework — TDD Evidence

## Source and scope

The user journey and acceptance criteria were derived from the conversational
plan approved on 2026-09-08/09. The task was to build a project-wide local
automation framework that does not depend on desktop control, permits guarded
real-database testing, and records the workflow in the AI rules. CI and release
workflow changes were explicitly excluded.

## User journeys

1. As the sole operator, I can run one local command that selects core, headless
   browser, or complete project checks.
2. As the operator, I can test with an empty database, a consistent copy of the
   real database, or the real database with an automatic backup and explicit
   write acknowledgement.
3. As a developer, I can build and typecheck the frontend without replacing the
   tracked production assets in `static/`.
4. As an AI coding agent, I have one authoritative testing rule that maps changed
   areas to required local verification and does not treat desktop-control failure
   as a reason to skip headless E2E.

## RED evidence

- Command: `python -m unittest discover -s tests -p "test_automation_framework.py" -v`
- Result: 6 tests ran and failed because `scripts/run_tests.py` did not exist.
- The failures directly represented the missing suite selection, database modes,
  environment normalization, quality commands, and CLI listing behavior.
- RED checkpoint: `aa5c0ac test: 定义自动化测试框架合同`.

Additional RED/GREEN regressions were captured while exercising the real entry:

- Worker startup initially produced 46 import errors because execution by script
  path omitted the repository root from `sys.path`. A contract now requires
  `python -m scripts.run_tests` worker startup.
- npm's child shell could not resolve Node in the current long Windows `PATH`.
  Quality commands now resolve and invoke Node directly.
- The first detached Vite build did not resolve Tailwind's content configuration.
  A contract now requires changing to the frontend directory before loading Vite.

## Coverage and known gaps

- The existing production-code baseline is 27.8%, below the 80% target for new
  or materially changed testable modules. The framework starts with a 20% global
  anti-regression floor and the AI rule requires 80% for changed testable logic.
- Browser E2E currently covers three modules and Chromium only. It does not test
  real Xianyu mutations, which remain unsuitable for the default automated suite.
- No CI or release workflow was changed, by explicit user request.
- Manual visual inspection remains separate and may be `NOT VERIFIED` when desktop
  control is unavailable; headless functional E2E is still mandatory.
