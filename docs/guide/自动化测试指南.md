# Local Automation Testing Guide

The repository uses one cross-platform entry point:

```powershell
python scripts/run_tests.py --list
```

It orchestrates the existing Python `unittest` tests, Python Playwright headless
browser tests, coverage, TypeScript, a detached Vite build, Compose validation,
and `git diff --check`. It also gives each run an isolated runtime log/static
directory and removes completed test artifacts older than seven days. It does
not use desktop control and does not modify CI or release workflows.

## Setup

```powershell
python -m pip install -r requirements-test.txt
python -m playwright install chromium
npm --prefix frontend ci
```

`requirements-test.txt` includes the runtime requirements plus Coverage.py.
The frontend continues to use the checked-in `package-lock.json`.

## Suites

```powershell
# Non-browser tests.
python scripts/run_tests.py --suite core --database snapshot

# Browser tests only; Chromium runs headless.
python scripts/run_tests.py --suite e2e --database snapshot

# All Python tests plus coverage and local project quality checks.
python scripts/run_tests.py --quality --database snapshot
```

`core` contains every `tests/test_*.py` module that is not listed in
`E2E_TEST_MODULES`. `e2e` currently contains the knowledge-base document flow,
the system-log page, the local captcha fixture flow, the real-page
password-login flow, and the stealth-script browser effect tests.
Adding a browser module requires adding its module name to `E2E_TEST_MODULES` in
`scripts/run_tests.py`.

For a focused RED/GREEN cycle, run the existing unittest discovery command:

```powershell
python -m unittest discover -s tests -p "test_<area>.py" -v
```

## Database modes

| Mode | Behavior | Use it for |
|---|---|---|
| `temp` | Creates an empty disposable SQLite database | Schema, migration, rollback, deletion and fault-injection tests |
| `snapshot` | Uses SQLite backup to clone the real database, including committed WAL state | Normal local regression with realistic schema and data shape |
| `live` | Connects directly to the real database after creating a timestamped backup | Explicit single-user live verification |

The normal mode is `snapshot`. Direct real-database execution is available with:

```powershell
python scripts/run_tests.py --suite core --database live --allow-live-writes
```

The acknowledgement is mandatory because importing the application can perform
initialization or migrations and many tests exercise writes. Before the worker is
started, a consistent backup is written below `backups/test-runs/`. The runner
does not restore it automatically because an automatic restore could overwrite a
legitimate change made while the test was running.

## Detached frontend build

The local quality run does not call the production `npm run build`, because that
command cleans and replaces tracked `static/index.html` and `static/assets/`.
Instead it invokes the local TypeScript compiler and
`frontend/scripts/build-test.mjs` directly through the resolved Node executable.
The build script changes its working directory to `frontend/` so Tailwind loads
the correct configuration, then writes the complete bundle below the current
test artifact directory.

## Coverage and artifacts

Every run creates `logs/test-artifacts/<run-id>/`. Depending on the selected
options, it contains:

- Python test output;
- `.coverage`, a text coverage report, and `coverage.xml`;
- detached frontend assets;
- output from TypeScript, Compose, and diff checks.

测试产物根目录的直接子项按 7 天清理；清理不跟随符号链接，也不处理根目录之外的路径。E2E 会先把当前前端构建到本次隔离产物目录，再由测试服务使用该目录，避免修改提交的 `static/`。

The production-code legacy baseline is currently about 27%. The full local gate
uses a 20% floor to catch broad regression while the repository is incrementally
improved. New or materially changed testable production logic should reach at
least 80% line and branch coverage in the changed module. Raise the global floor
only after the measured full-suite result supports it.

Artifacts and disposable databases are ignored by Git. They are diagnostic data,
so do not intentionally write credentials, cookies, buyer messages, card values,
or API secrets into them.

## Result interpretation

- `PASS`: the command executed and returned zero.
- `FAIL`: a test or required local gate returned non-zero.
- `NOT VERIFIED`: a prerequisite was unavailable and the corresponding command
  was not executed.

A desktop-control initialization failure affects only manual visual inspection.
It does not block the headless Playwright suite. A missing Chromium installation
must be reported as `NOT VERIFIED`, not as a browser test pass.
